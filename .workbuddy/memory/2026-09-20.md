## 真机（realme RMX2121）部署与连接模式语义
- 真机 adb 序列号 `RWPRTCMVSWQWMJBA`（Android 12/API31，arm64）。原版 `4.0.M1.3` 与我们的 debug 签名冲突，**必须先卸载再装**；已备份原包到 `_backup_original_phone.apk`。

- 真机日志监控方式：`adb logcat -v time -b main -b system -b crash > _phone_logcat.txt` 后台跑（Bash 工具在本机 PortableGit 下 `ls` 等命令不可用，用 PowerShell 读文件）。
- **三种连接模式的真实语义**（源码确认，jadx_out）：
  - `5`=热点 → `a.a.a.a.m.m.e.a` (WirlessProtocolTransport)：**仅监听 UDP 7999 广播**等手机端来包，或 `a.a.a.a.l.b.g`(phoneIp) 非空时直接连该 IP。
  - `9`=直连 → `a.a.a.a.m.m.d` (InstantProtocolTransport)：WiFi P2P + 蓝牙交换信令（`Bluetooth_CarLife_SDK` 日志）。

  - 选择逻辑在 `a/a/a/a/m/m/b.java` 第160行 `B0("CONNECT_TYPE")`。
- **车机端 APP 完全不开热点**：grep `setWifiApEnabled|startSoftAp|WifiApConfiguration|SSID|getConnectionInfo` 全部无匹配。所以热点模式只要求"车机与手机同网段"，**车机连手机热点、或手机连车机热点，两种方向都可行**；风险在于手机端 CarLife App 若强制要求先连上名为 CARLIFE_xxx 的车机热点才发起广播，则会卡在等待。

## 「手机伪装成车机」身份识别机制（关键）
- **直连模式下车机端从不主动 P2P connect**：`a/a/a/a/n/i/c/a.java` 只有 `discoverPeers()`；`WifiDirectDiscoverableTask`(m/m/d/h.java) 名字骗人，实际是循环 discoverPeers。发起方一定是手机端 CarLife+。
- **车机身份靠这几个 config 传递**（默认全为空 → 手机端认不出）：
  - `CONFIG_WIFI_DIRECT_NAME`：经蓝牙通道交给手机端，手机端按此名发 P2P 连接。
  - `CONFIG_HU_BT_NAME` / `CONFIG_HU_BT_MAC`：HU(Head Unit) 身份，通过 `CarlifeFeatureConfigList`(`m/k/a/e.java` setHuBtName/setHuBtMAC) 发给手机端。
  - `CONFIG_TARGET_BLUETOOTH_NAME`：车机端 `BluetoothDeviceDiscover`(m/m/d/a.smali) 遍历**已配对**蓝牙设备找同名者，用 SPP UUID `00001101-0000-1000-8000-00805F9B34FB` 主动连（非空才连，空则直接 return）。
  - 取值点：`CarlifeActivity` 里 `a.a.b.r.a.d().g("XXX")`；SDK 侧从 `m/m/d/d.java` 的 lazy 字段 `f`=`I0("CONFIG_TARGET_BLUETOOTH_NAME")` 读。
- **Android 12 上 App 改不了蓝牙名**（`BluetoothAdapter.setName` 需 BLUETOOTH_PRIVILEGED）与 WiFi 直连名（API 已移除）→ 只能手动改系统设置或 root。
- realme 实测：`settings get secure bluetooth_name`=`realme X7 Pro`；热点 SSID 同且 `hiddenSSID=true`（必须关掉隐藏）；`wifi_p2p_device_name`=null。
- **绕开设备类型识别的最优路线 = USB AOA 有线**：realme 具备 `android.hardware.usb.host`，App 已声明 `<uses-feature usb.host>` + `res/xml/device_filter.xml` 是 `<usb-device/>`（匹配任意设备）+ 无障碍服务 `UsbAccessibilityService` 自动授权 USB。OTG 线连另一台手机即可，手机端检测到配件必定弹 CarLife（系统级行为，不判断对方是否车机）。

## 直连(WLAN P2P)投屏逻辑全链路审查（静态代码，未抓真机日志）
- **所有 CONFIG_ 的真正来源 = `assets/bdcf`**，不是 SP、不是硬编码！`a/a/b/r/a$a`(Thread) 里 `assetManager.open("bdcf")` 逐行解析：第一个非 `#` 行存入字段 `F`(channel id，不参与 split，所以 bdcf 第2行裸 `20352101` 不会崩)，之后每行 `trim→去空格→跳过空/#→split("=")→put(parts[0],parts[1])` 填进 `HashMap G`。`g(key)`/`f(key)` 从 G 读；G 里没有就返回 null / 静态字段初值。
- **当前 bdcf 实际内容**：`CONFIG_WIRLESS_TYPE=3`(支持热点+直连)、`CONFIG_WIRLESS_FREQUENCY=1`(5G)、`CONFIG_HU_BT_NAME=xxx`、`CONFIG_HU_BT_MAC=yyy-zzz-xxx`(占位假值)、`VOICE_MIC=1`、`CONNECT_TYPE_ANDROID=1`；**缺 `CONFIG_WIFI_DIRECT_NAME`、缺 `CONFIG_TARGET_BLUETOOTH_NAME`**。
- **协议时序（直连）**：①车机 discoverPeers 循环 ②车机做 SPP client(`createRfcommSocketToServiceRecord(00001101-…)`) 连手机 ③手机问 1048577→车机回 1081346(wirelessType/频率) ④手机问 1048580→车机回 1081349 带 `CONFIG_WIFI_DIRECT_NAME` ⑤手机按该名发起 P2P connect ⑥组建成→车机收 CONNECTION_STATE_CHANGE ⑦经蓝牙发 1081350 要 IP ⑧手机回 1048583 带 IP ⑨车机建 7 条 TCP(7240/8240/9240/9241/9242/9340/9440，见 `m/m/e/b.java` 的 f185a)。
- **确认的缺陷**：
  1. `m/m/d/e.java:207` `if (this.d == null) return;` —— `CONFIG_WIFI_DIRECT_NAME` 为空则**不回复** 1048580，手机端拿不到车机 P2P 身份→不会发起连接（头号阻塞点）。
  2. `m/m/d/e.java:170` `a(WifiP2pInfo)` 里 `if (this.f == null) return;` —— P2P 组建成但蓝牙 communicator 未就绪就静默放弃，**无任何重试**（对应真机 17:19 组建成后车机静默）。
  3. `m/m/d/a.smali` run() 开头 `adapter==null||!isEnabled()` → 打 `so return` 直接结束，蓝牙通道彻底放弃（仅收到 STATE_ON=12 才重启调度）。
  4. 同上第236行：targetName 非空但 getBondedDevices 无同名设备 → 直接 return，**不重试**。
  5. targetName 为空的 fallback：反射 `BluetoothDevice.isConnected()`（隐藏 API，Android12 大概率被拦），catch 后**默认返回 true** → 所有配对设备都尝试 SPP，对端没监听就 1s 重试刷日志。
  6. `CONFIG_WIRLESS_FREQUENCY=1`(5G)，但 Android P2P 基本跑 2.4G，手机端若只搜 5G 会搜不到。
  7. targetSdk=30 + Android12：P2P 走 ACCESS_FINE_LOCATION appop，后台时 foreground-only → 系统拒收 CONNECTION_STATE_CHANGE（已实测 Appop Denial）；manifest 未声明 ACCESS_BACKGROUND_LOCATION。
- **我们自己的补丁对该链路无副作用**：`b.j()` 默认值改 `getDefaultType()` 只影响 `B0("CONNECT_TYPE",2)` 兜底；`g.c()` 日志 hook 只做拼接+post，不参与连接判定。
