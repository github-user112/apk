### 无线直连的真实链路（两版架构一致，约 9 步）
车机蓝牙 RFCOMM 主动连手机 → 手机问无线类型 → 车机答 wirlessType(=3 都支持)/频率 →
手机问车机 WiFi 直连名 → 车机答 CONFIG_WIFI_DIRECT_NAME → 车机 discoverPeers 待命 →
手机按名发起 P2P 组网（**手机当 GO**，如 DIRECT-SO-xxx，192.168.49.1）→ 手机经蓝牙回传 IP →
车机 TCP 连手机 7240/8240/9240/9241/9242/9340/9440（`WirlessConnector`）开始投屏。
结论：**蓝牙是无线连接的带外握手通道，不是可选项。**

### 1.6 直连失败的根因（截图日志为证）
1. `【蓝牙】蓝牙未开启，跳过蓝牙通道 ← bluetoothAdapter?.isEnabled: false, so return`
   —— `BluetoothDeviceDiscover.discoverDevice()` 首行即返回，全链路无法启动。
2. `车机WiFi直连名称: 未配置` —— `assets/bdcf` 配置文件中**根本没有 CONFIG_WIFI_DIRECT_NAME 项**。
3. `assets/bdcf` 里 CONFIG_HU_BT_NAME=xxx、CONFIG_HU_BT_MAC=yyy-zzz-xxx 仍是占位符。
4. `CONFIG_WIRLESS_FREQUENCY = 1`（5G）—— 老车机 P2P 多只支持 2.4G，应改 0。
5. 热点模式 1.6 只能被动等 UDP 广播，无「手动 IP」兜底；有线模式失败是 AOA 切换问题（另一条线）。
- assets/bdcf 现有关键项：CONNECT_TYPE_ANDROID=1、CONFIG_WIRLESS_TYPE=3、CONFIG_WIRLESS_FREQUENCY=1、
  CONFIG_HU_BT_NAME、CONFIG_HU_BT_MAC、AUDIO_TRACK_TYPE、VOICE_MIC 等（UTF-8，key = value 文本）。

### v1 包的两个真实缺陷（已在 v2 修复，务必保留教训）
1. **补丁 B 无效**：`d.smali` 的 `onReceive` 收到蓝牙 `STATE_ON(12)` 后要检查标志 `d.h`，只有 `h==true` 才 `postDelayed(runnable,1000)` 重试。

   v2 改为：`if-nez v1, :p2p_name_len` → 非空去查长度；null/空串都回退 `CarLife-HU`。

### realme/ColorOS 的操作坑（重要）
1. **adb 静默安装被拦截**：`pm install` 会挂住并弹出 realme 自家安装引导页 `com.oplus.appdetail/.model.guide.ui.InstallGuideActivity`，

   不要匹配单独的"安装"二字（会误装推荐 App）。见 `_rl_swap.sh`。
2. **屏幕灭屏时 shell 命令会静默卡死**（`pm install` 卡 11 分钟无输出）。先 `input keyevent KEYCODE_WAKEUP` + `input swipe` 解锁。
3. **`input tap` 完全无效**，必须用 **`input touchscreen tap X Y`**（这是本轮最大坑，卡了很久）。

5. 安装后的危险权限（位置/录音）默认全 false，**不给位置权限 P2P 扫描会失败**，必须先授权再测。

### 【核心发现】Android 12 的 WifiP2pService 系统级权限收紧
```
E/WifiP2pService: Permission violation - none of NETWORK_SETTING, NETWORK_STACK,
                  or OVERRIDE_WIFI_CONFIG permission, uid = 10262
```
- 这三个是 signature|privileged 权限，**第三方应用永远拿不到**。
- 触发者是 1.6 老 SDK 自己的 P2P 调用（`WifiDirectDiscoverableTask` → `WifiP2pOperationSequence`），
  **不是**我加的补丁 —— 做过去掉补丁 C 的对照实验（v3），`Permission violation` 依旧出现。
- 后果：`WifiDirectDiscoverableTask onFailure 0`(ERROR) → 每秒 `DiscoverPeers` → `onFailure 2`(BUSY) 死循环 →
  界面"等待 WLAN 直连组网中…" → 最终**"连接超时，请重新连接。"**（与用户车机现象完全一致）
- 旁证：`dumpsys wifi` 里 `numPersistentGroup=1`，且 `ip link` **没有 p2p0 接口** → `p2pFind` 必然失败 → BUSY。

### 关键对照实验（三次装机，条件一致：直连模式 + 位置/录音权限已授）

| 原版 1.6 | ❌ 从不启动（connect 后无后续） | ❌ 无 | 静默卡住 |

→ 说明**补丁让流程前进了**（原版连 P2P 待命都没走到），但 Android 12 的权限墙挡住了组网。

### v3 补丁 = v2 + 补丁 C 加系统版本保护
`_patch_v3.py`（基线 `_sm16` → `_w19`），补丁 C 增加：
```
sget v2, Landroid/os/Build$VERSION;->SDK_INT:I
const/16 v1, 0x1d          # 29
if-lt v2, v1, :p2p_name_done
```
理由：`WifiP2pManager.setDeviceName()` 是 `@hide` + `@UnsupportedAppUsage` 隐藏 API，
Android 10+ 调用会被 WifiP2pService 拒绝。改为**仅 API<29 调用**：车机 4.4.2(API 19) 照常生效，Android 10+ 跳过。
自检脚本里注意：**寄存器越界检查要先剔除 `#` 注释行**（`patchC(v3)` 里的 "v3" 会被 `\bv(\d+)\b` 误判）。

### 亿连基础信息
- 包名 `net.easyconn`，versionName `7.0.1-9011d330b-202404121051`
- **minSdk 16 / targetSdk 28 → 原生支持 API 19**，单 dex 2051 类，42.6 MB
- so：`libECSDK.so`（核心服务）、`libmediaserver.so`、`libtun2socks.so`、`libDnsProxy.so`、`libjni-helper.so`
- 特点：`uses-feature android.hardware.bluetooth_le required=true`；**内嵌 jmdns 3.4.1**（约 60 类）
- 配置全在 `assets/EcConfig.prop`，由 `f.a.i.m.g.h0()` 懒加载进静态 `Properties f2936c`

### 亿连的直连六步（核心）
1. `EcWifiManager.h()` → `discoverPeers()`（前置检查 WiFi 开 / 未在搜 / 传输未开 / 未被强停）
2. `EcWifiManager.c(WifiP2pInfo)` → **GO 双向兼容**：自己 GO → reOpenWifiService；自己 Client → 取 `groupOwnerAddress`
3. `Message(what=45)` 设 IP，传输类型 `EC_TRANSPORT_ANDROID_WIFI`
4. `q.W()/q.X(i)/q.Y()` = openWifiService / 延迟open / reOpenWifiService
5. **`ecsdk/WifiManager.d()` publishMdns ← 灵魂**：
   等 IP（500ms 轮询）→ 枚举网卡按 displayName 过滤 → `JmDNS.create(addr,hostAddr)`
   → `ServiceInfo.create("_EasyConn._tcp.local.", "EasyConn", port, "Wifi Discovery Service for EC")`
6. 手机解析 mDNS → 拿 **IP + 动态端口**（来自 `ECSDK.native_getLocalServiceInfo()` 的 port）→ TCP 连

### 亿连的关键设计（都可借鉴）
- **端口是动态的**，由 mDNS 携带，不存在"端口不对"
- **`MulticastLock` 22 处** + 既 publish 又 `addServiceListener`（双向发现）
- **120 秒周期重试**：`EcWifiManager.a` Runnable 每 120000ms 检查传输未开就重新 search
- 广播监听 10 个 action（含 `WIFI_AP_STATE_CHANGED`、`CONNECTIVITY_CHANGE`）
- 断开收尾：`removeGroup` + `clearLocalServices` + `stopPeerDiscovery`
- **绝不调隐藏 API**：`setDeviceName` 一次都没用。反过来用 `requestDeviceInfo`（且 `SDK_INT>=29` 保护）
  **读**系统设备名，再 `changeCarNavigatorName()` 把系统名认作自己的名字
- **4.4.2 上根本不用蓝牙**：`EasyConnectService.onCreate()` 里 `SUPPORT_QR_BLE_AP` 分支第一句
  `if (Build.VERSION.SDK_INT < 21) { log("...does not support BLE"); return; }`（此时 EcWifiManager 已构造完）
- `EcConfig.prop`：`ENABLE_APP_WIFI_DIRECT=true` / `ENABLE_SDK_WIFI_DIRECT=false` /
  `ENABLE_WIFI_SERVICE=true` / `SUPPORT_BT_CALL=false`
  → 唯一会 `createGroup` 的 `ecsdk/d.java` 被配置编译期关掉，**运行时根本不实例化**

### CarLife 1.6 的决定性反证
| 能力 | 亿连 | CarLife 1.6 |
|---|---|---|
| JmDNS | 329 | **0** |
| MulticastLock | 22 | **0** |
| ServerSocket | 12 | **0** |
| WifiP2pDnsSdServiceInfo | 3 | 0 |
| createRfcommSocket | 0 | **2** |
| BluetoothSocket | 4 | **13** |
| setWifiApEnabled | 2 | **0** |

CarLife 全 dex 用到的 WifiP2pManager API 仅：`initialize`(2) / `discoverPeers`(1) /
`stopPeerDiscovery`(1) / `requestConnectionInfo`(1) / `cancelConnect`(1)；
**`createGroup`=0、`addLocalService`=0、`connect`=0、`requestPeers`=0**。

且 CarLife 车机端全 dex **只有一个 `java.net.Socket`（在 `a.a.a.a.a.j.f.c`）且无 ServerSocket**，
构造是 `new Socket(String host, int port)` → **车机是 TCP 客户端，host/port 只能由蓝牙给**。

### 一句话结论
亿连用「**网内 mDNS 服务发现**」自举 → 不依赖蓝牙；
CarLife 用「**蓝牙 RFCOMM 带外信道**」自举 → 蓝牙一断全链路终止，且车机纯被动（不建组、不广播、不等 GO 反转）。

### 给后续改造的优先级（若开工）
1. 补网内自举：车机起 ServerSocket → jmdns/NSD 广播 `_xxx._tcp`（带 port TXT）→ 手机解析 → TCP 连
   （这条路 P2P / 热点 / 同网 WiFi 全兼容，且不需要任何隐藏 API）
2. 车机从"纯被动"改为必要时候 `createGroup`，并兼容自己当 GO
3. 加 120 秒级周期重试（CarLife 目前单次超时即死，无自愈）
4. 加 MulticastLock（无组播锁 mDNS 会被 WiFi 过滤）
5. 断开时 removeGroup + clearLocalServices + stopPeerDiscovery，避免残留组导致下次 BUSY

## 新增：亿连 V7.0.1（车机端）「WiFi传输速率低 → 断连」逆向分析（只分析，未改代码）

### 需求
用户用亿连 7.0.1 车机端时，连一会儿就弹「WLAN速率低」然后断连。要求：这是什么情况 + 怎么分析日志 + 怎么改（先不动代码）。

### 分析对象（重要：这个 APK 是车机端）
`亿连手机互联V7.0.1.apk`，包名 **`net.easyconn`**（车机端，LAUNCHER=`net.easyconn.ui.StandMainActivity`）；
配套手机端 = **`net.easyconn.carman`**（亿连驾驶助手），见 `assets/EcConfig.prop` 的 `PHONE_APP_PKG`。
反编译：jadx 出 `_jx_yl/sources`（3293 个 java）；apktool 出 `_dec_yl`（含 classes.dex / res / lib）。

### 核心结论
«WiFi传输速率低» **不是测带宽，是 ping 往返时延监控**：
- 字符串 `res/values/strings.xml: wifi_low_speed_tip = "WiFi传输速率低"`
- 弹出点 `f.a.k.l0.p3.w()`（MirrorFragment）→ `showToast`；`p3.z()` 只是隐藏占位 View
- 触发者 `f.a.k.m0.r0.o()`，线程名 **`Mirror_Presenter_Ping_Service`**：
  `while(volatile s)` → `ECSDK.ping(对端IP, 250)` 测耗时 dt → **dt>200ms 记 1 次**（正常则清零）
  → **连续 3 次**弹提示 + 埋点 `EC_MIRROR_SUCCEED_WIFI_LOW_SPEED_TIP`，i 清零 → `Thread.sleep(2000)`
  → 最快约 6 秒弹出。另有 dt>200ms 时 `postDelayed(z(), 3000)` 把提示藏掉。
- ping 是 **native**：`Java_net_easyconn_ecsdk_ECSDK_native_1ping`，在 **`libECSDK.so`**
- 提示**不含任何断开逻辑**；断连另有路径：
  原生 `[CtrlSocket]/[DataSocket]/[C2PSocket]/[P2CSocket] onDisconnect: ... code=%d`
  → `[%s]onMirrorDisconnected: post event ET_STATUS_MIRROR_DISCONNECTED`
  → Java `f.a.i.i.m.onMirrorDisconnected()` → `r0.x(4)`（日志 `MirrorPresenter onMirrorDisconnected reason = 4`）
  → 界面显示 `yltp_status_tip4_txt1 = 屏幕镜像已断开`
- 结论：**同因两果**（WLAN 链路劣化同时触发"提示"和"断连"），不是提示导致断连
- 重连很弱：`p3.onMirrorRequestReconnect()` 是**空实现**；只有 `onPhoneAppExited` 延迟 2000ms 重开 transport，
  且 USB 受 `APP_USB_EXITED_RECONNECT` 门控。协议里有 `supportMirrorReconnect` 标志。
- 劣化早期信号（native 字符串）：`AirplayModel::recvMirrorThread(), running data inavailable mMirrorPause=%d, mMirrorDroped=%d`、
  `header failed.`、`value is lost,value=%d`
- 心跳：`[C2PService]startHeartbeat` / `heartbeat request already pending` / `peer does not accept heartbeats`

### 日志抓手（已确认）

### 补充（smali 级追查后的两处修正 + 新发现）
为追线程启动点，用 `tools/apktool.jar d "亿连手机互联V7.0.1.apk" -o _yl_sm --no-res --no-assets` 额外生成了 smali 树
（`_yl_sm/smali/`，可复用于 smali 级改动）。据此修正：

1. **监控线程的启动点不是 r0 自己，而是 `f.a.i.i.q.l0()`（= `startMirror()`）**
   - `q.smali:5742 l0()`：`startMirror()` 返回 0 → `handler.post(r0.a)` → 判断 `q.H().name().contains("WIFI")`
     → `r0.s = true`（唯一置 true 处）→ 懒建 `ThreadPoolExecutor(1,1,1s,LinkedBlockingQueue, r0::m, r0::s)`
     → `execute(new f.a.k.m0.m(r0))` → `r0.o()`
   - `r0.s`（volatile）全包只有 3 次访问：`<init>` 置 false、`q.l0()` 置 true、`r0.p0()` 置 false
   - 线程名来自 ThreadFactory lambda `f.a.k.m0.t` → `r0.m(Runnable)` → `new Thread(r, "Mirror_Presenter_Ping_Service")`
   - 任务 lambda `f.a.k.m0.m.run()` → `r0.o()`
2. **「WiFi传输速率低」只在 WiFi 通道出现**
   `ECTransportType` 里 `name().contains("WIFI")` 命中的是 `ANDROID_WIFI(2)`（直连/热点都算）、`IOS_WIFI_APP(6)`、`IOS_WIFI_AIRPLAY(7)`；
   USB(0/1/3/4/5/8)、`MIRACAST(9)`、`DLNA(10)`、`BLE(11/13)`、`BTRFCOMM(12)` 都不启动监控 → 有线永远不弹。
3. **断开原因码**：`g0.i0(4)` = `m.onMirrorDisconnected()`（镜像断开）；`g0.i0(5)` = `q.l0()` 里 `startMirror()` 返回非 0（启动失败，
   返回值有 `-1/-2/-3/-7` 专门分支）→ 这几个负数是"起不来"的直接线索。
