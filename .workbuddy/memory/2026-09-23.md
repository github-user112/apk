## 二维码打不开的根因（已定位，待修 → 计划 1.19）

用户报「日志下载的还是不行，手机端打不开你给的二维码」。

根因在 `logxfer_src/java/.../LogHttpServer.java` 的 `localIps()`：
它遍历 `NetworkInterface.getNetworkInterfaces()` 返回**所有**非回环 IPv4——
**不区分网卡、不排序、不过滤蜂窝**（`rmnet0` 的 `10.x` 也在里面）。`baseUrls()` 把前 3 个
拼成 `http://<ip>:18080`，`LogDownloadActivity.buildAssetUrl()` 用 `,` 连接塞进
`file:///android_asset/logxfer/logxfer.html#<u1,u2,u3>`，`logxfer.html` 就渲染**最多 3 个二维码**
（每个 190×190）。用户扫到的大概率是**手机根本路由不到的那个 IP**。

叠加因素：日志下载要求手机与车机**同网**。而按 1.18 的诊断，蓝牙 SPP 不通 → 手机压根没 join
进 P2P 组 → 车机的 `192.168.49.1` 手机也路由不到。**所以"打不开"多数情况下是网络层没通，
不是二维码算法错。**

1.19 要改：
1. `localIps()` 按"手机可能可达"排序并过滤：优先 `p2p0`/`192.168.49.x` → `wlan0`/`192.168.x.x`
   → 其它；**排除 `rmnet*`/蜂窝网段**
2. 页面只给**一个主二维码**（推荐地址），其余降级为小字列表 —— 一屏 3 个码只会让人不知道扫哪个
3. 界面上把**网卡名**一起显示（`p2p0: 192.168.49.1`），并加一句"手机需先连上车机 WiFi Direct 组"
   的前置条件提示，便于现场判断是"地址错"还是"网络没通"

### ★ 最重要的教训：Dalvik 过 = 真机不一定过

1.18 的蓝牙插桩（四件套 `new-array + const/4 + aput-object + invoke-static`）在
**1.2/1.3 处复用了 v3 当数组索引却没重置**，而 `d/a.run()` 里 v3 被用 29 次、中间已变成引用类型
→ 合并点类型冲突。

| 环境 | 运行时 | 结果 |
|---|---|---|
| 车机 4.4.2 / MuMu 4.4.4 | **Dalvik** | 校验宽松，**完全测不出来** |
| realme Android 12 | **ART** | 直接拒类 `VerifyError: Invalid reg type for array index` |

→ **新写/改动的 smali 类，必须至少在一台 ART 设备上跑一遍启动**。
`verify_dalvik_合并点检查.py` 只是静态近似，不能替代真机。

修法（1.20）：**插桩不再碰任何局部寄存器** —— 在 `ConnLog` 里加
`logLine(String)` + 9 个零参包装，插桩点变成一行
`invoke-static {}, Lcom/baidu/carlifevehicle/ConnLog;->logXxx()V`。零寄存器操作数，verifier 无从挑剔。
同时把 1.18 写坏的控制流改回 `if-nez v0, :cond_1b`（1.18 写成 `if-eqz` + 紧跟同名标签 + `goto :cond_1b`，
把原有的 **1 秒重试整个跳过了**，是功能回归）。

### 1.21 的根因：符号链接导致同一文件被收两遍

`refreshFiles()` 登记 6 个目录，其中
`getExternalFilesDir(null)/log` 与硬编码的 `/sdcard/Android/data/<pkg>/files/log`
**指向同一目录**（`/sdcard`、`/storage/sdcard0` 都是 `/storage/emulated/0` 的符号链接）。
去重键用 `getAbsolutePath()` → 两种写法字符串不同 → **去重失效** → 同一文件进 `mFiles` 两次
→ `ZipOutputStream` 重名条目抛异常。

修法：新增两个静态助手
- `canonicalKey(File)`：优先 `getCanonicalPath()`（真能解符号链接），失败退回手工归一化
  `/sdcard/`、`/mnt/sdcard/`、`/storage/sdcard0/` 三种别名前缀（用 `"前缀".length()` 而非硬编码下标）
- `uniqueName(List, String)`：zip 条目重名时补 `_2`/`_3`，扩展名挪到最后

## 17:00 追查界面「系统繁忙，请稍后再试」的真实含义（诊断结论）

- 文案出处：`ConnLog.logP2pBusy()`（`smali/com/baidu/carlifevehicle/ConnLog.smali:1168`），
  由 `logP2pCreateFail(2)` 调用 → 只对应 createGroup 回调的 **reason=2 (BUSY)**。
  另有一处同文案在 `logP2pDiscoverFail(I)` 的 reason=2（discoverPeers 失败，目前无调用点）。
- 调用链：`j$b.run()` createGroup → 系统 P2pStateMachine → onFailure(2) → logP2pCreateFail(2)
  → logP2pBusy() → 界面日志区「⚠ 系统繁忙，请稍后再试」。
- ★实测真因（realme X7 Pro / Android 12）：这台机**一直开着 WiFi 热点**
  （`SoftApManager iface=ap0 role=ROLE_SOFTAP_TETHERED`、`softAp=true`），
  导致 **`dumpsys wifip2p` 的 curState 常年停在 `P2pDisabledState`**（WiFi 开着也不 enabled）；
  在这种状态下 createGroup 被系统挡回，AOSP 报的是 **BUSY(2) 而不是 P2P_UNSUPPORTED(1)**。
  所以「系统繁忙」是**误导性文案**——真机既不忙也不重试无望，而是 P2P 根本没启用。
  这同时解释了 1.27 时网卡摘要为什么是 `ap0=192.168.227.155`（那时就在开热点）。
- 诊断命令（车机上照抄即可）：
  `adb shell dumpsys wifip2p | grep -E "curState|groupFormed"` + `adb shell cmd wifi status`
  正常应为 `curState=P2pEnabledState`；若在 `P2pDisabledState` 就必然 BUSY。
- 车机排查要点：**车机若自身开了热点，P2P 会被射频占掉**（单 radio 互斥），
  这是「直连」与「热点」两个模式互相打架的硬件层原因，App 侧只能提示、无法绕过。
- 未做（待用户定）：把文案改成更准确的「⚠ 直连未就绪(可能热点占用/未启用)，正在重试」，
  以及在 `precheck()` 里加一条「P2P 未启用/正处于 SoftAP」检测。
