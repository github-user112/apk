# 1.15 直连 vs 5+ 版直连：对齐度核对

> 核对对象：`CarLife4.0车机端个人修改版1.15_5+流程移植.apk`（versionCode 115，基于 1.6 / minSdk 16）
> 对照：`百度CarLife4_v2026.01.06.2006_共存_安卓5+.apk`（`com.muyetuge.carlifevehicle`，minSdk 21）
> 结论日期：2026-09-22

---

## 一、一句话结论

**协议层本来就同源，这次移植把"连上之后保活"补齐后，直连主链路的阶段 0–6 已经对齐。**
但**不能说"完全一致"**——仍有 **2 项没有对齐**（都是"用户可见的提示层"，不影响能否连上），
而我们在组网与清理上**比 5+ 多 7 项能力**（5+ 没有）。

所以准确表述是：**主链路对齐，加固方向互补。**

---

## 二、逐阶段对齐矩阵

| 阶段 | 5+ 的做法 | 1.15 现状 | 对齐 |
|---|---|---|---|
| 0 前置自检 | `m7/f0`：蓝牙权限/邻近设备权限/WiFi 开关/P2P 初始化，逐项中文提示 | 无前置自检，直接尝试；失败靠日志 | ❌ 未对齐 |
| 0' 被动建组自救 | ❌ 全仓 0 处 `createGroup` | ✅ `d.j` 自举器：无组则自己建组当 GO | ✅ 我们更强 |
| 1 蓝牙带外 SPP | 蓝牙没开就**直接 return，不重试** | ✅ patchB：自动 `enable()` 后继续 | ✅ 我们更强 |
| 2 P2P 发现/建组 | `WifiP2pOperationSequence` stop→discover 串行 | ✅ **原生已有**：`n/i/b` 序列，stop 失败同样降级 onSuccess | ✅ 对齐 |
| 3 组形成 + IP 交换 | 空 IP 且已连组 → 延时重发 `requestIp` | ✅ **原生已有**：`m.m.d.e :cond_6` + 1s(`0x3e8`) | ✅ 对齐 |
| 4 TCP 直连 + 保活 | 1s 发 `0x20002`；30s 无收包 → terminate | ✅ **1.15 补上**：`m.m.e.f` 2s 发 `0x20002`、30s(`0x7530`) 超时 → terminate | ✅ 对齐 |
| 5–6 业务会话/清理 | 只 `stopDiscoverable + cancelConnect` | ✅ `removeGroup + clearLocalServices + release 组播锁 + 停定时器 + 停自举器` | ✅ 我们更强 |
| 贯穿：设备名对齐 | `DeviceInfoListener`（API29+）读系统名回填 | ✅ **1.15 补上**：API14 的 `WIFI_P2P_THIS_DEVICE_CHANGED_ACTION` 广播兜底 | ✅ 等价对齐 |
| 贯穿：发现失败重试 | 固定 2000ms，无上限 | 递增退避 6/8/10/12/14s，上限 6 轮 | ⚠️ 策略不同（我们更省电，但恢复慢） |
| 贯穿：错误提示 | `m7/e0` 中文分级提示（"当前设备不支持WLAN直连"/"系统繁忙，请稍后再试"） | 仅 `CarLifeP2PBoot` 日志分级，界面无提示 | ❌ 未对齐 |

## 三、能力对比（谁有什么）

### 3.1 1.15 独有的（5+ 没有）— 7 项

| # | 能力 | 说明 |
|---|---|---|
| 1 | **createGroup 自举器** | 手机不建组时车机自救；5+ 完全被动等 |
| 2 | **组播锁 MulticastLock** | 5+ 全仓 0 处 |
| 3 | **DNS-SD `addLocalService`** | 5+ 全仓 0 处 |
| 4 | **蓝牙未开自动 `enable()`** | 5+ 蓝牙没开直接放弃 |
| 5 | **`setDeviceName` 正向改名** | 4.4 上可用；5+ 因 API29+ 限制只能反向读 |
| 6 | **terminate 清理彻底** | 我们 removeGroup + 清 service + release 锁 + 停三个定时器 |
| 7 | **USB 免授权四层降级** | 5+ 走 AOA accessory，另一条路 |

### 3.2 5+ 独有的（1.15 没有）— 2 项

| # | 能力 | 影响 | 4.4 可移植性 |
|---|---|---|---|
| 1 | **前置自检 + 中文提示**（`m7/f0` / `m7/e0`） | 用户能看到"为什么不连"；现在只能看日志 | ✅ 可移植，但 `NEARBY_WIFI_DEVICES` 是 API33，需裁掉该分支 |
| 2 | 发现失败**无限重试**（2s 固定） | 车机 Wi-Fi 慢热时 5+ 更"死磕" | ✅ 可改，但会持续唤醒射频 |

## 四、MuMu 实测结果（1.15，Android 4.4.4）

### 4.1 直连模式（默认）

自举器**回归基准全命中**，分支方向正确：

```
15:38:58.085 D/CarLifeP2PBoot: armed: HU will createGroup() and act as GO if no group appears
15:38:58.085 D/CarLifeP2PBoot: discover loop cancelled (free P2P state machine)
15:38:58.089 D/CarLifeP2PBoot: MulticastLock acquired (non reference counted)
15:38:58.089 E/CarLifeP2PBoot: addLocalService failed (ignored)
15:39:06.093 D/CarLifeP2PBoot: createGroup attempt 1/6          ← 关键：无组时必须走到这行
15:39:06.093 E/CarLifeP2PBoot: createGroup failed, reason=1     ← MuMu 不支持 P2P 的预期失败
15:39:06.093 E/CarLifeP2PBoot: P2P UNSUPPORTED by driver -> give up, please use hotspot or USB
15:39:06.093 D/CarLifeP2PBoot: disarmed: lock+service+group cleaned
```

心跳看门狗按预期启动：

```
15:38:58.089 D/CarLifeHB: heartbeat watchdog started (period 2000ms, timeout 30000ms)
```

界面自检四行全对（`CarLife-HU` 设备名 / `CONNECT_TYPE=9` 直连 / 连接引擎启动 / 【直连】开始建立 P2P 通道），
最终走到 `MainFragment:【超时】连接超时` —— MuMu 无 Wi-Fi Direct，属预期。
**零崩溃**（无 `FATAL` / `VerifyError` / `NoSuchClassDefFound`）。

### 4.2 切到热点模式（验证状态机与"停表"锚点）

点「热点」页签后：

```
15:43:57.145 D/CarLife_SDK: setConnectType, 5
15:43:57.145 D/CarLifeHB: heartbeat watchdog stopped          ← ★ 停表锚点确实可达
15:43:57.145 D/CarLifeP2PBoot: disarmed: lock+service+group cleaned
15:43:57.145 D/CarLife_SDK: WifiP2pManager terminate
15:43:57.145 D/CarLife_SDK: InstantProtocolTransport terminate
15:43:57.145 D/CarLife_SDK: WirlessProtocolTransport connect listener
15:43:57.145 D/CarLife_SDK: start read broadcast socket
15:43:57.145 E/CarLifeWifi: MulticastLock acquire failed (ignored)
```

一次干净的**模式切换状态机**：停心跳 → 拆 P2P 传输 → 收自举器 → 起无线（热点）传输。
也**顺带证明了 `heartbeat watchdog stopped` 这条锚点真的会被触发**——它是通过基类
`a.a.a.a.j.c;->f()V` 的虚分派到达 `d.f()` 的（调用点在 `m.m.b:235/423`），不是死代码。

### 4.3 MuMu 验不到的部分（必须上车机）

| 项 | 为什么 MuMu 验不了 |
|---|---|
| 心跳**发包**路径（`g(b)` 发送 `0x20002`） | 需先"收到过对端包"（`f.c==1`）才进入发包/超时判定；MuMu 无 P2P 永远收不到 |
| 心跳**超时**自愈（30s → terminate） | 同上，判定门槛过不去 |
| `WIFI_P2P_THIS_DEVICE_CHANGED_ACTION` 设备名兜底 | MuMu P2P 不支持，该广播永不发出 |
| P2P 组网、蓝牙 SPP 带外 | MuMu 均不支持 |

> 这三个未覆盖路径**已在 dex 里静态校验过方法引用全部存在**：
> `m.m.e.d;->g(La/a/a/a/a/a/b;)V`（344 行）、`a/a/a/a/a/a/b$a;->b(...)La/a/a/a/a/a/b;`（27 行，`public static synthetic`，dex 可正常解析）、
> `a.a.a.a.n.h;->b(Ljava/lang/Runnable;JJ)V`（76 行）、`h;->c(Ljava/lang/Runnable;)V`（108 行）、`h;->a`（7 行）。
> 且 `h.b()` 是**每任务新建独立 Timer**（非共享），异常不会污染其他定时任务。

## 五、剩余差异的处理建议

| 优先级 | 项 | 建议 |
|---|---|---|
| 中 | 失败分级的**界面提示** | 值得做：车机上用户看不到日志。把 `CarLifeP2PBoot` 已有的分级结果透出到界面（reason=1 → "当前设备不支持 WLAN 直连"；reason=2 → "系统繁忙，请稍后再试"） |
| 低 | 发现失败无限重试 | 先实测；若车机慢热能连上就不改（省电优先） |
| 低 | 前置自检 | 可选；4.4 只需蓝牙/WiFi 开关两项，把 API33 权限检查删掉 |

**结论**：如果只问"直连能不能按 5+ 的流程走通"，答案是**能，阶段 0–6 已对齐**。
如果问"是否一模一样"，答案是**不**——差 2 项提示层，多 7 项加固。
