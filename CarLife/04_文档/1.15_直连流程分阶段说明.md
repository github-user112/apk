# CarLife 车机端「WLAN 直连」分阶段流程（1.15 对齐新版 5+ 流程）

> 蓝本：`百度CarLife4_v2026.01.06.2006_共存_安卓5+.apk`（`com.muyetuge.carlifevehicle`，未混淆）
> 落点：`CarLife4.0车机端个人修改版1.15`（`com.baidu.carlifevehicle`，全混淆）
> 硬约束：**minSdk 保持 16，全程兼容 Android 4.4.2（API 19）**
>
> 一句话：**协议层两版同源**（同一套蓝牙带外消息号、同一张端口表、车机同为 TCP 客户端），
> 1.15 的工作是**把新版流程里"连上之后保活"这一段补齐**，同时保留我们自己在"被动建组 + 彻底清理"上的优势。

## 二、逐阶段详述

### 阶段 0 · 前置就绪 + P2P 自举

| | 说明 |
|---|---|
| **新版做法** | `m7/f0.a()` 逐项自检（蓝牙权限 → 邻近设备权限 → 定位 → WiFi 开关 → `WifiP2pManager.initialize()`），失败给中文提示 |
| **1.15 做法** | 读 `assets/bdcf` 配置 → `setDeviceName(CarLife-HU)`（仅 API<29）→ 取组播锁 → 起自举器 |

### 阶段 1 · 蓝牙带外通道（SPP）

蓝牙是**无线连接的带外握手通道，不是可选项**——WiFi 名字、频率、IP 全靠它交换。

| | 说明 |
|---|---|
| **新版做法** | `BluetoothDeviceDiscover`：**没有扫描环节**，只在 `getBondedDevices()` 里按名字精确匹配；蓝牙没开就只打日志 **直接 return，不引导开启** |
| **1.15 做法** | 保留扫描 + **蓝牙未开自动 `enable()`**（patchB），并修正 enable 后的状态位 `d.h` |
| **锚点** | `d.smali`（蓝牙发现）· `d/a.smali run()`（patchB） |
| **UUID** | `00001101-0000-1000-8000-00805F9B34FB`（两版一致） |
| **4.4 说明** | `BluetoothAdapter.enable()` 在 4.4 无需系统签名，可用 |
| **相对新版差异** | 新版蓝牙没开就放弃 → **这点我们明显更强**（车机冷启动场景必现） |

---

### 阶段 2 · P2P 发现 / 建组

| | 说明 |
|---|---|
| **新版做法** | `WifiDirectDiscoverableTask`：`WifiP2pOperationSequence` 串行跑 `[StopPeerDiscover → DiscoverPeers]`，`AtomicBoolean` 防重入；stop 失败降级当成功；失败固定 2s 周期重排 |
| **1.15 做法** | 1.6 原生已有同构队列（`n/i/b` + `n/i/c/{b,a}`，stop 失败同样降级为 onSuccess）→ **无需移植**；额外用 patchF 静态开关 `j.n` 抑制发现重排风暴 |
| **锚点** | `h.smali`（发现任务）· `j.smali`（自举器）· `i.smali onReceive`（patchG） |
| **4.4 说明** | `WifiP2pManager.discoverPeers/stopPeerDiscovery/createGroup` 全部 API 14+，4.4 原生支持，**且 4.4 没有 Android 12+ 的 `NETWORK_SETTING` 权限墙** |
| **相对新版差异** | 我们多一个自举器（新版没有）；新版队列更优雅（我们有，但实现更土） |

自举器分级（1.11 patchH + 1.14 修复分支方向）：

```
createGroup onFailure:
  reason == 1 (P2P 不支持)  → 放弃，打日志
  reason == 2 (BUSY)        → removeGroup + 递增退避重试（6/8/10/12/14s），上限 6 次
```

### 阶段 3 · 组形成 + IP 交换

```
WifiP2pInfo.groupFormed == true
  → 车机蓝牙发 0x108006 (RequestIp) 向手机要 IP
  → 手机回 0x100007 (ResponseIp)
     ├─ IP 非空            → 交给 WirlessConnector 建 TCP
     └─ IP 为空 且 组已连  → 延时 1s 重发 requestIp   ← IP 就绪轮询
```

| | 说明 |
|---|---|
| **锚点** | `e.smali d(...)`（发 `0x108006`，547 行）· `e.smali :cond_6`（312 行，1s 重发）· `e.smali a(WifiP2pInfo)` |
| **4.4 说明** | 无 API 依赖问题 |
| **结论** | **IP 就绪轮询 1.6 原生就有**（`:cond_6` + `0x3e8`），新版那条不需要移植 |

带外消息号对照（两版**完全一致**）：

| serviceType | 方向 | 语义 | 1.15 分发分支 |
|---|---|---|---|
| `0x100001` | 手机→车机 | 无线信息请求 | `:sswitch_3` |
| `0x100004` | 手机→车机 | 目标信息请求（车机回 `CarlifeWirlessTarget`） | `:sswitch_2` |
| `0x100007` | 手机→车机 | 回报 IP | `:sswitch_1` |
| `0x100008` | 手机→车机 | 回报无线状态 | `:sswitch_0` |
| `0x108006` | 车机→手机 | 请求 IP | `e.smali d(...)` |

### 阶段 4 · TCP 直连 + 保活（🆕 1.15 主要增量）

**端口表**（两版一致；新版多出 9340/9440）：`1→7240  2→8240  3→9240  4→9241  5→9242  6→9340  7→9440`

**保活（1.15 新增，对齐新版 `ConnectionEstablishHandler`）**

| 项 | 新版 5+ | 1.15 |
|---|---|---|
| 协议号 | `MSG_VIDEO_HEARTBEAT = 0x20002` | `0x20002` ✅ 同号 |
| 发送周期 | 1000ms | **2000ms**（更省电，2s 内必有一次收包刷新） |
| 超时判定 | `now - lastRecv > 30000ms` → `terminate()` | `now - lastRecv > 30000ms`（`0x7530`）→ `d.f()` terminate |
| 阈值来源 | SP `CONNECT_HEARTBEAT_TIMEOUT` | 常量（4.4 上不做 SP，少一层失败点） |
| 定时器 | 裸 `java.util.Timer` ⚠️ | 我们自己的 `a.a.a.a.n.h` 调度器 ✅ |

**1.15 心跳实现（新类 `a/a/a/a/m/m/e/f.smali`）**

```java
// 静态方法
f.a()V                  // touch：收到任何包 → 刷新时间戳 + 置 c(已收包)=true
f.a(La/a/a/a/m/m/e/d;)V // start：幂等(b 已 true 则 return) → 2s 周期任务
f.b(La/a/a/a/m/m/e/d;)V // send：构造 0x20002 → d.g(msg) 发送，try/catch 兜住
f.b()V                  // stop：清标记 + 取消 Timer

// f$a.run() 每 2s:
//   b(运行中) 为 false          → return
//   c(已收包) 为 true           → return（首包未到不计时）
//   now - last >= 30000         → f.b() 停表 + d.f() terminate → 触发 patchK 自愈
//   now - last <  30000         → f.b(d) 发心跳
```

**插桩点（3 处，均为一两行）**

| 位置 | 插入 | 作用 |
|---|---|---|
| `e/b.smali c()` 收包尾部 | `f->a()V` | 任何收包刷新看门狗 |
| `e/d.smali a()` connect 尾 | `f->a(d)` | 直连成功起表 |
| `e/d.smali f()` terminate 头 | `f->b()` | 断开停表（防僵尸 Timer） |

**4.4 说明**：全部是 `System.currentTimeMillis` / `Timer` / 静态字段，无 API 依赖；`0x20002` 走原有消息构造路径，不新增协议。

**⚠️ 为什么不照抄新版的 Timer**：新版 `TimerUtils` 用裸 `java.util.Timer`（单线程），**一个 task 抛未捕获异常会干掉整个 Timer 线程**，之后所有定时任务静默失效。我们用 `a.a.a.a.n.h` 规避。

### 贯穿项 · 设备名对齐（🆕 1.15 新增兜底）

老问题的根：`WifiP2pManager.setDeviceName()` 在 API 29+ 被禁，新版只能**反向读**系统 deviceName 回填配置。
我们在 4.4 上 `setDeviceName` **可用**（patchC），但存在"设置失败 / 被系统改名"的窗口 → 1.15 补一条反向兜底。

| | 说明 |
|---|---|
| **新版做法** | `m7/d0` 用 `DeviceInfoListener`（API 29+）读系统 `deviceName` |
| **1.15 做法** | **`WIFI_P2P_THIS_DEVICE_CHANGED_ACTION` 广播**（API 14+）→ `EXTRA_WIFI_P2P_DEVICE` 里取 `deviceName` 存静态兜底 |
| **锚点** | 新类 `a/a/a/a/m/m/d/m.smali`；插桩 `i.smali onReceive` 新增 `THIS_DEVICE_CHANGED` 分支 + `e.smali` 两处取值兜底 |
| **4.4 说明** | `WIFI_P2P_THIS_DEVICE_CHANGED_ACTION` 是 API 14，**4.4 原生支持**；`DeviceInfoListener` 不可用，故用广播 |

```java
m.a(Intent)V                     // 从广播取 WifiP2pDevice.deviceName → 静态字段 a（非空且非空串才存）
m.a(String)Ljava/lang/String;    // 配置值非空 → 原样返回；空 → 返回系统兜底值
```

## 四点五、构建产线（1.15 重建时踩出来的坑，已固化进脚本）

构建 1.15 的过程中发现了一个**会静默产出残缺 APK** 的严重问题，值得单独记下来。

### 事故：`_w115` 丢了 350 个文件

上一轮从 `_w114` 复制工程时进程被超时杀掉，留下的是**整份文件不存在**的工程（不是内容损坏）：

```
缺 smali/com/baidu/**  307 个   ← 全部是 protobuf 生成类
缺 unknown/META-INF     43 个
```

apktool **照样打包成功、签名成功、APK 只小 139 KB**（不显眼），但装上必然 `NoClassDefFoundError`。
根因是我当时的"修复"只比对了**两边都存在**的文件做 md5 —— 整份缺失的文件根本不在比对集合里，
**必须做集合差** `set(参照) - set(目标)`。

### 另一处静默丢文件：`robocopy /XD build`

按**名字**排除目录会误伤正常路径：

```
unknown/META-INF/com/android/build/gradle/app-metadata.properties
                            ^^^^^ 这个目录也叫 build
```

必须写**绝对路径** `/XD "$PRJ/build"`。

### 沙箱的批量删除保护

一次 `rm` 影响超过约 50 个文件会被拦截并返回非 0，**bash 脚本内部的 `rm` 同样被拦**。
旧 build.sh 里的 `rm -rf $WORK` 被拦后不报错、脚本继续跑，于是 `_build_w` 永远残留；
下一轮 `cp -r` 因为目标已存在而**嵌套成 `_build_w/_w115`**，apktool 就拿着旧内容打包
—— 这是"改了没生效"的头号来源。

### 现在的做法

```bash
# 1) 完整性门禁（缺失就补齐，有计划外差异就终止）
python 校验并补齐工程.py _w115 _w114 --fix

# 2) 每轮构建用全新时间戳目录，纯复制、从不删除
WORK="$ROOT/_bw_${TAG}_$(date +%s)"
robocopy "$PRJ" "$WORK" /E /XD "$PRJ/build" /R:0 /W:0 /NFL /NDL /NJH /NJS /NC /NS /NP
```

构建脚本 `03_构建脚本/build.sh` 已按上面改好（带 `REF=` 参数即自动跑门禁）。

### 产物必须做"条目级"对比

```bash
jar tf new.apk | sort > /tmp/new.txt
jar tf old.apk | sort > /tmp/old.txt
comm -23 /tmp/old.txt /tmp/new.txt    # 少了什么（必须为空或每项可解释）
```

**只看文件大小会被骗**：1.11~1.15 五个版本的 APK 大小全是 `2540650` 字节，
而缺 350 个文件的残包也只小 139 KB。1.15 的最终校验结论：

| 校验项 | 结果 |
|---|---|
| APK 条目数 | 1.14 = 686，1.15 = 686，**零差异** |
| classes.dex | 1,570,632 → **1,571,924**（+1,292 字节 = 心跳 + 设备名兜底） |
| dex 字符串 | `CarLifeHB`、`heartbeat watchdog started`、`heartbeat timeout 30s`、`system p2p deviceName captured as fallback`、`THIS_DEVICE_CHANGED` 全部命中 |
| 签名 | v1 + v2 + v3 全部通过 |
