# 1.17 说明：把「下载日志」做进 CarLife 主界面 + 日志清理机制

> 版本：`versionCode 117` / `versionName mod1.17`
> 成品：`CarLife/05_产物/CarLife4.0车机端个人修改版1.17_日志下载入口.apk`
> 基线：`_w116`（1.16）→ 工程树 `_w117`，补丁脚本 `02_补丁脚本/patch_v14_日志按钮.py`
> 最后更新：2026-09-22

---

## 1. 一句话

1.16 的「扫码下载日志」功能是对的，但**入口做错了**：它给 `LogDownloadActivity` 挂了
`MAIN/LAUNCHER` intent-filter，装完会在车机桌面上多出一个独立图标，看着像另一个 App。
1.17 把入口改成 **CarLife 主界面右上角的一个按钮 —— 位置在「方控」左边，文字「下载日志」**，
并去掉那个独立图标；顺带在下载页加了「返回」按钮和日志体积统计。

## 2. 用户诉求 vs 1.16 的做法

| 用户诉求 | 1.16 的做法 | 1.17 的修正 |
|---|---|---|
| 加到百度 CarLife app 里，不要单独一个 app | Activity 挂了 `MAIN/LAUNCHER`，桌面多一个图标（包还是同一个包，不是独立 app） | 去掉 intent-filter，`exported="false"`，改成主界面内按钮 |

  （因为挂了 LAUNCHER）。1.17 把这个图标去掉了。

## 3. 按钮是怎么挂上去的（关键，换方法容易踩坑）

### 3.1 主界面结构

`res/layout/frag_main.xml`（另有 `res/layout-hdpi/frag_main.xml` 变体）在右上角依次排了三个
TextView，从右到左是：

| 按钮 | id | 说明 |
|---|---|---|
| 帮助 | `0x7f0900a3` | `@string/baidu_help` |
| 设置 | `0x7f0900a4` | `@string/diy_set` |
| 方控 | `0x7f0900a2` | `@string/diy_button`（`strings.xml:104`，值为 `<u>方控</u>`） |

### 3.2 为什么不去改 onClick 的 packed-switch

点击分派在 `a/a/b/n/s.smali`（MainFragment）的 `onClick` 里：

```
a/a/b/n/s.smali:875   .packed-switch 0x7f0900a2
                          :pswitch_2      # 方控 -> a/a/b/n/h
                          :pswitch_1      # 帮助 -> a/a/b/n/q
                          :pswitch_0      # 设置
```

往 `packed-switch` 里插一个 case 要重排跳转表、改索引基准，静态核对困难，
一旦算错就是 `VerifyError` 直接崩。**所以不碰它。**

### 3.3 采用的路径：复用 `ConnModeHelper.init(root)`

`a/a/b/n/s.smali:378` 本来就有一行：

```
invoke-static {p2}, Lcom/baidu/carlifevehicle/ConnModeHelper;->init(Landroid/view/View;)V
```

`ConnModeHelper` 是**我们自己写的类**（1.11 加直连/热点/有线那排按钮时建的），
它的 `init(root)` 拿到的正是 `frag_main` 的根 View，方法体里已经有一串
`root.findViewById(...)` 在挂东西。于是在它的入口插**一行**：

```
    invoke-static {p0}, Lcom/baidu/carlifevehicle/logxfer/LogXferEntry;->bind(Landroid/view/View;)V
```

`LogXferEntry.bind(root)` 负责 `findViewById(0x7f090147)` + `setOnClickListener`。
好处：

- 不动 MainFragment，不动别人的 `packed-switch`，只动我们自己的类；
- 不需要新的权限、不需要反射；
- 按钮不在布局里时 `findViewById` 返回 null，只打一条 warn 日志，不影响启动。

### 3.4 新增的资源 id

`main_btn_logxfer = 0x7f090147`，写在两处（必须同步）：

- `res/values/public.xml`：`<public type="id" name="main_btn_logxfer" id="0x7f090147" />`
- `res/values/ids.xml`：`<id name="main_btn_logxfer" />`

> ⚠️ 这个工程是 apktool 工程，我们的 Java 源码（`logxfer_src/java`）是拿 javac 独立编译的，
> **没有 R.java**，所以 `LogXferEntry.ID_MAIN_BTN_LOGXFER` 里是硬编码的 `0x7f090147`。
> 改一处就要改三处，`patch_v14_日志按钮.py` 与 `构建日志下载smali.py` 都带了一致性自检。

### 3.5 按钮的排布

两个布局变体都加了，用 `layout_toLeftOf` 而不是再算一个 `layout_marginRight`，
这样不管按钮多宽都紧贴在「方控」左边：

```xml
<TextView android:id="@id/main_btn_logxfer"
    android:layout_toLeftOf="@id/main_btn_button"
    android:layout_width="wrap_content" android:minWidth="84.0dp"   <!-- hdpi 变体是 56.0dp -->
    android:layout_height="84.0dp"                                  <!-- hdpi 变体是 56.0dp -->
    android:background="@drawable/com_bg_btn_selector"
    android:gravity="center" android:textSize="20.0sp"              <!-- hdpi 变体是 16.0sp -->
    android:text="下载日志" />
```

文字直接写在布局里（和「直连」「热点」「有线」一样的做法），不新增 string 资源。

### 3.6 顺手修的三个 bug（两个在 ConnModeHelper，一个是本轮新代码自己犯的）

做这次验证时盯着主界面截图才发现「当前版本」一直显示 `mod1.6`，追下去是两个老 bug；后面那个是本轮新写代码自己犯的。

**bug1 —— 分支方向写反（这个项目第四次踩了）。** 原 smali 是：

```
    const v0, 0x7f090146                      # conn_ver_text
    invoke-virtual {p0, v0}, Landroid/view/View;->findViewById(I)Landroid/view/View;
    move-result-object v0
    check-cast v0, Landroid/widget/TextView;
    if-nez v0, :cond_5                        # <-- 反了
    ... getPackageInfo ... setText(...)
```

`if-nez` 的语义是「v0 不为 0 就跳走」。也就是说 **TextView 找到的时候反而跳过 setText**，
只有找不到（null）时才往下走 —— 而 null 走到 `setText` 必然 NPE 被 catch 吞掉。
净效果：那句 setText 永远执行不到，界面一直显示布局里写死的 `mod1.6`。
正确写法是 `if-eqz`（找不到才跳）。

> 记一下这个坑：`if-eqz` = 等于 0 就跳；`if-nez` = 不等于 0 就跳。
> 这类错误静态检查抓不到（布局和 id 都对），只能靠真机/模拟器上看一眼。

**bug2 —— 版本号拼串少了一段。** 原字面量是 `"当前版本: "`，刷出来变成
`当前版本: mod1.17`，把 `4.0.M1.3` 这段基础版本号丢了。补成 `"当前版本: 4.0.M1.3-"`，
最终显示 `当前版本: 4.0.M1.3-mod1.17  [二次开发版]`。

**bug3（本轮新写的代码自己犯的）—— `summary()` 读了一个还没创建的实例。**
第一版 `summary()` 里写的是 `LogHttpServer s = sInst;`，但 `sInst` 是在 `get()` 里
惰性创建的，而 `get()` 第一次被调用是在 `Activity.onStart()`，`summary()` 却是在
`onCreate()` 里调的 —— 所以拿到的一直是 null，统计行永远渲染成空字符串。
改成 `LogHttpServer s = get();` 才对。**这个 bug 在截图上表现为「那一行什么都没有」，
不报错、不崩溃，很容易漏掉。**

## 5. CarLife 的日志清理机制（回答「难道一直增长吗」）

**结论：不会一直增长，有一套完整的轮转 + 淘汰机制。** 代码在
`a/a/a/a/n/g.smali`（`CarLife_SDK` 这个 tag 的 Logger，Kotlin 写的）。

### 5.1 三个参数

在 `a/a/a/a/a/e.smali:364-442` 构造 Logger 时设定：

| 参数 | 字段 | 默认值 | 含义 |
|---|---|---|---|
| `CONFIG_LOG_LEVEL` | `g` | `5` | 日志级别 |
| `CONFIG_MAX_LOG_FILE_SIZE` | `h` | `0x500000` = **5 MB** | 单文件大小上限 |
| `CONFIG_MAX_LOG_FILE_COUNT` | `i` | `0x14` = **20** | 目录内文件数上限 |

### 5.2 落盘位置（API 19 车机）

`a/a/a/a/a/e.smali` 里按 SDK 版本分支：

- `SDK_INT > 21`：`getExternalFilesDir(null)/log`
- 否则（**4.4 车机走这支**）：`getFilesDir()/log`
  → `/data/data/com.baidu.carlifevehicle/files/log/`

文件名 = 时间戳 + `.log`，例如 `2026-09-22T15:38:57.079Z.log`。

### 5.3 轮转逻辑（`a/a/a/a/n/g.smali` 的 `f(String)`，约 500-1050 行）

每写一条日志后检查：

```
if (当前文件.length() > 5MB) {
    关闭 writer
    把 <名字>.log  gzip 成 <名字>.log.gz 并删除原文件     # 第 737 行 delete()
    列出目录内所有文件，【排除文件名含 "crash" 的】
    按 lastModified() 升序排序                            # g$b 比较器
    if (文件数 >= 20) {
        n = 文件数 * 0.2                                  # 20 -> 4
        if (n > 0) 删掉最旧的 n 个                         # 第 989 行 delete()
    }
}
```

- 删除阈值用 `>=`，步长 20%：文件数到 20 → 删 4 → 剩 16 → 再长到 20 → 再删 4。
  所以**稳态是 16~20 个文件**。
- 排序按 `lastModified()`（`g$b.smali`，取 `File.lastModified()` 做差），**删的是最旧的**。
- 每个文件压缩前最大 5MB，gz 之后日志文本一般压到原体积的 1/8~1/15，
  所以**磁盘占用是「几十 MB 原始量级 → 实际几 MB」**，不会失控。

### 5.4 两个需要知道的「例外」

**(1) 5MB / 20 这两个值在 `assets/bdcf` 里改不了。**

`CONFIG_MAX_LOG_FILE_SIZE` 和 `CONFIG_MAX_LOG_FILE_COUNT` 这两个字符串在整个 dex 里
**只出现在读取处**（`a/a/a/a/a/e.smali:404` / `:426`），没有任何地方往配置 map 里塞它们
—— `CarlifeActivity` 从 bdcf 转发给 SDK 的 key 只有这 8 个：

```
CONFIG_WIFI_DIRECT_NAME, CONFIG_TARGET_BLUETOOTH_NAME, CONFIG_HU_BT_NAME, CONFIG_HU_BT_MAC,
CONFIG_LOG_LEVEL, CONFIG_WIRLESS_TYPE, CONFIG_WIRLESS_FREQUENCY, CONFIG_SAVE_AUDIO_FILE
```

所以日志体积/数量上限**永远取默认值 5MB / 20 个**。想改只能改 smali：

- `a/a/a/a/a/e.smali:397` 的 `const-wide/32 v2, 0x500000`（5MB）
- `a/a/a/a/a/e.smali:419` 的 `const/16 p2, 0x14`（20 个）

（对比：`CONFIG_LOG_LEVEL` 走的是 bdcf → `CarlifeActivity` → SDK 这条链，是能改的。
不过 Logger 里的 `g` 字段只被写过、从没被读过，属于死字段。）

**(2) 有一个「无清理逻辑」的日志写入器，但默认是关的。**

`a/a/a/a/l/c.smali` 会往 `/sdcard/BaiduCarlife/<yyyy-MM-dd>_Carlife.log` 追加写
（一天一个文件，`FileWriter(path, true)`），**这个函数里没有任何删除逻辑**。
但它的开关是静态字段 `b`：

- `b` 只在类初始化时被设成 `6`（`l/c.smali:30-32`），全工程没有第二处赋值；
- 写入条件是 `b <= 3`，`<clinit>` 里置 `c`（目录）为 null 的条件是 `b > 3`。

**所以这个写入器在本包里恒为关闭状态**，`/sdcard/BaiduCarlife` 根本不会被创建。
MuMu 实测印证：`ls /sdcard/BaiduCarlife` → 不存在。

### 5.5 实测占用

MuMu 上装 1.16 跑了约 1 小时：

```
/data/data/com.baidu.carlifevehicle/files/log/
-rw------- u0_a49 u0_a49  63620  2026-09-22 16:47  2026-09-22T15:38:57.079Z.log
```

**只有 1 个文件，63 KB。** 按 5MB 单文件上限估算，跑满 20 个文件、每个都压满，
也就是十几 MB 的量级。

### 5.6 唯一一个理论上的漏洞

清理时**排除文件名含 `crash` 的文件**（`n/g.smali:827` 和 `n/b.smali:105` 两处过滤器）。
如果有别的组件往这个目录写 `xxx-crash.log`，那些文件**不会被计数、也不会被删**。
不过在整个 dex 里 `"crash"` 只出现在这两个过滤器里，没有任何地方写这种文件
（`CarlifeStatisticsInfoProto` 里的 `crashLog_` 是协议字段，不是文件名），
所以实际上这个漏洞目前是空的。要真担心，可以在下载页看到文件列表时留意一下。
