## 0. 结论速览

| # | 症状 | 根因（定位结论） | 1.18 做了什么 | 还需要什么才能 100% 确认 |
|---|---|---|---|---|
| 1 | 直连：截图上「组网成功 + 等待手机发起连接」→ 连接超时 | **阶段1 蓝牙 SPP 带外握手没做成**。手机拿不到 SSID/PSK 就不会去 join 组，车机 GO 只能干等超时 | 给蓝牙阶段三处**静默早退**补日志；配对列表为空时**每 5s 自愈重试** | 车机上的完整日志（尤其 `[阶段1]` 那几行） |
| 2 | 点「热点」页签卡死 | `selectMode()` 在 **UI 线程**上同步跑 停旧任务(`removeGroup`/停定时器) + 建新任务(绑 socket) + `SharedPreferences.commit()` fsync | 新增 `ConnSwitchTask(Thread)`，整条切换链挪到**后台线程**；`commit()` → `apply()` | 车机上再点一次热点，看是否还卡 |

## 1. 症状1：直连组网成功但手机不加入

### 1.1 截图已经排除的

截图里能看到：

```
isGroupOwner: true
GO 地址: 192.168.49.1
组名: DIRECT-ch-CarLife-HU
✔ WLAN 直连已组网，等待手机发起连接
```

这说明 **阶段0 自举（`createGroup` 当 GO）和阶段2 建组全部走通了** —— 1.11 的 P2P 自举、
1.14 的分支方向修复在真车机上全部生效。车机侧 P2P 没问题。

问题在**手机侧为什么不 join**。

### 1.2 为什么一定是蓝牙（阶段1）

CarLife 的无线直连是**带外握手**模型：

```
车机 createGroup 当 GO  ──┐
                          ├─ 蓝牙 SPP 把 SSID / PSK / GO MAC 交给手机（0x100001）
手机 join 这个 P2P 组   ──┘
手机拿到 IP → 车机收到 0x100007 → 阶段5 建 7 条 TCP 通道
```

也就是说：**蓝牙没通，手机就永远不知道要 join 哪个组**，车机只能等到超时。
截图里没有任何蓝牙相关日志 —— 这与下面的代码路径完全吻合。

### 1.3 代码定位：三处「静默早退」

`a/a/a/a/m/m/d/a.smali`（`BluetoothDeviceDiscover.run()`）里有三处**不打任何日志**就
`return` 的分支：

| 位置 | 触发条件 | 原行为 |
|---|---|---|
| `:goto_5` / `:cond_1b` | 配了 `CONFIG_TARGET_BLUETOOTH_NAME`，但**没有任何已配对设备**名字与它相等 | 静默 return |
| `:cond_1a` / `:cond_1b` | `getBondedDevices()` 为空（车机从没和手机配对过） | 静默 return，**且永不重试** |
| `:cond_1a` / `:cond_1b` | 已配对设备全部 `connect()` 失败，且 `d/d.h == 0` | 静默 return |

**为什么"屏幕上没看到蓝牙日志"这条判断是可信的**：SDK 的日志器
`La/a/a/a/n/g;->c(ILjava/lang/String;[Ljava/lang/Object;)V` 已经被桥接到
`ConnLog.log()`（`a/a/a/a/n/g.smali:455`），也就是说 **SDK 的 `CarLife_SDK` 日志会原样出现在
车机屏幕上**。所以屏幕上看不到 = 代码真的没走到打日志的地方。

> 顺带说明：`1.15` 文档里"待办2：用户提供车机蓝牙名/MAC → 填 bdcf"这条已**降级**。
> `CONFIG_HU_BT_NAME/MAC` 只在 `m/k/a/e`（连上之后发给手机的 feature config）里用，
> **不是连接阻塞点**。

### 1.4 1.18 的改动

1. **补日志**（走 `n/g$a.a` → ConnLog，车机屏幕可见）：
   - 阶段1 入口：`==== [阶段1] 蓝牙带外握手: 开始扫描/连接手机 ====`
   - 目标名无匹配：`⚠ [蓝牙] 未找到名为 CONFIG_TARGET_BLUETOOTH_NAME 的已配对设备, 跳过握手`
   - 连接结果：`✔ [蓝牙] SPP 已连上, 进入带外握手(SSID/PSK/IP 交换)` /
     `⚠ [蓝牙] SPP 连接失败(见上一条 exception)`
   - 无配对设备：`⚠ [蓝牙] 车机无已配对设备: 请先在 车机蓝牙设置 里与手机配对(每5s重试)`
   - 全部失败：`⚠ [蓝牙] 已配对设备全部连不上(手机端 CarLife 打开了吗?)`
2. **空配对列表自愈**：原来「一个已配对设备都没有」是**死路**（不重试）。1.18 改成
   每 **5s**（`0x1388`）用 `Handler.postDelayed(d/d$c, 5000)` 重试一次。
   → 用户可以「先打开车机 App，再去车机蓝牙设置里配对手机」，App 会自己接上，不用重启。

### 1.5 车机侧需要用户配合的两件事（这是设计如此，不是 bug）

1. **手机必须先和车机做蓝牙配对**（系统级配对，不是 CarLife 内部配对）。
   配对成功后，`getBondedDevices()` 才有内容。
2. **手机端 CarLife 要处于"无线连接 / 等待连接"状态**，否则车机连上 SPP 也没人应答。

## 2. 症状2：点「热点」页签卡死

### 2.1 调用链（全部在点击回调 = UI 线程上）

```
TextView.onClick
└─ ConnModeHelper$ClickHandler.onClick
   └─ ConnModeHelper.onModeClicked(id)
      └─ ConnModeHelper.selectMode(5)          ← UI 线程
         ├─ highlight()
         ├─ m/b;->b()  → 返回 m/c 实例
         ├─ m/c;->i(5)
         │   └─ m/d;->i(I)                     ← UI 线程
         │      ├─ G("CONNECT_TYPE", 5)
         │      ├─ m/m/b;->j()                 ← 停旧任务: 逐个 task.f()
         │      │   · 直连任务 e/d.f(): 停心跳表 / unbind BT socket /
         │      │     停自举器 / cancelConnect + removeGroup + stopPeerDiscovery
         │      └─ m/m/b;->V()                 ← 起新任务: task.a()
         │          · 热点任务 e/a.a(): new DatagramSocket(7999) + Thread.start()
         └─ SharedPreferences$Editor.commit()  ← 同步 fsync 落盘
```

`m/m/b.j()` 的形态（`j.smali:386`）：

```smali
:goto_0
if (list 非空) { list.remove(0).f(); goto :goto_0 }   # 排空旧任务
then switch(CONNECT_TYPE) 建新任务 → list.add(...) → c.q(type)
```

写在这里的都是**同步**动作。单纯看每一句都不慢，但叠在弱车机 + 一次 `commit()` fsync 上，
就足以触发 ANR —— 用户感知就是「点下去就卡死」。

### 2.2 1.18 的改动

1. **新增 `com/baidu/carlifevehicle/ConnSwitchTask`（继承 `Thread`）**，
   把 `m/b;->b()` + `m/c;->i(mode)` 整条链挪到后台线程：
   ```smali
   # ConnModeHelper.selectMode() 内
   new-instance v0, Lcom/baidu/carlifevehicle/ConnSwitchTask;
   invoke-direct {v0, p0}, Lcom/baidu/carlifevehicle/ConnSwitchTask;-><init>(I)V
   invoke-virtual {v0}, Lcom/baidu/carlifevehicle/ConnSwitchTask;->start()V
   ```
   线程名 `CarLifeSwitch`，内部 `try/catch Throwable`，并打「开始/完成/异常」三条日志。
2. **`SharedPreferences$Editor.commit()` → `apply()`**：去掉 UI 线程上的同步 fsync。

> 线程安全说明：`m/d.i()` 内部只有 `SharedPreferences` 写、`WifiP2pManager` 的 channel 异步调用、
> `Handler.post`、`new DatagramSocket` 和 `Thread.start()`，都不要求主线程；
> 三条链路的 `a()`（直连 `e/d` / 热点 `e/a` / 有线 `m/m/c/a`）也没有主线程依赖
> （有线链路用的是 `AtomicBoolean`）。

## 3. 症状3：热点连不上

### 3.1 定位

对 `_w117` 全仓扫描：

```
WifiManager;->addNetwork      → 0 处
WifiManager;->enableNetwork   → 0 处
WifiConfiguration             → 0 处
```

对 CarLife 5+ 参考实现同样扫描：只有 `l8/o.smali` 读 `WifiConfiguration`，**没有** `addNetwork`。

结论：**车机端（1.6 和 5+ 都一样）不会自己连手机热点。**
热点模式的正确用法是：

- 手机开热点 → **用户在车机 WLAN 设置里手动连上它**，或
- 车机开热点 → 手机连车机 AP

然后车机在 `UDP 7999` 上收手机的广播（`m/m/e/a$a.run()`），拿到手机 IP 后建 TCP 通道。

### 3.2 1.18 的改动

不动架构，只补足可观测性：

- `==== [阶段4] 热点模式启动: 建 UDP 7999 监听 ====`
- `✔ 热点模式: UDP 7999 监听线程已启动`（若是走了 `catch SocketException`，会先打
  SDK 自带的 `connect error:` + 异常，说明 **7999 端口被占**）
- `⏳ 热点模式: 已监听 UDP 7999, 等手机广播/拿IP(需车机WLAN先连上手机热点)`
- 收到广播时 SDK 原本就会打 `connect  packet:<手机IP>`

有了这几条，下次车机测试就能一眼看出是「没连上热点」还是「连上了但广播没到」。

## 4.5 顺带修好的「门禁」缺陷（重要）

`verify_dalvik_合并点检查.py` 原来有两处问题，这次把它扩大覆盖范围时暴露了出来：

| 问题 | 表现 | 修法 |
|---|---|---|
| 「Zero/null」类型建模错误 | `const/4 vX, 0x0` 被当成 **INT**，而 apktool 反编译出来的代码里**普遍用它当 `null`**，于是一旦某个寄存器在汇合点上是 `null` / 引用两种来源，就被误判为 CONFLICT。把 `d/a.smali` 加进清单后一次报 **36 条**假冲突 | 新增 `NULL` 类型：「Zero/null 与 int 或引用合并 = 对方类型」。Dalvik 真实语义就是这样 |
| 错误重复收集 | 不动点迭代每轮重扫所有块并 `errs.append`，同一条错误被报 **3 遍**（12 条 × 3 = 36） | 结束时按首次出现顺序去重 |
| 「缺少文件」当成错误 | `TARGETS` 是**跨版本累积**清单，老版本工程里没有 1.15/1.18 才新增的文件，于是 rebuild 老版本会被门禁误杀 | 降级为「跳过」提示；工程完整性由 `校验并补齐工程.py` 专门负责 |

同时 `TARGETS` 从 10 个文件补到 **16 个**，把 1.15 起所有手工插桩点（`d/a`、`e/b`、`e/d`、`e/f`）
和 1.18 新增的 `ConnSwitchTask` / `ConnModeHelper` 都纳入进来。
回归：`_w111` / `_w115` / `_w117` / `_w118` 全部通过。

## 5. 车机上怎么验（下次实测清单）

1. 装 1.18，进主界面。
2. **先看蓝牙**：随便切一次模式，往上翻日志，找 `==== [阶段1] 蓝牙带外握手 ====`。
   - 若下面跟 `⚠ 车机无已配对设备` → 去车机蓝牙设置配对手机，**不用重启 App**，等 5s。
   - 若跟 `⚠ 已配对设备全部连不上` → 检查手机端 CarLife 是否处于等待连接状态。
   - 若跟 `✔ SPP 已连上` → 蓝牙通了，问题在更后面（把完整日志拿回来）。
3. **再点热点**：看是否还卡。若仍卡，说明卡点不在 `selectMode`，需要 logcat / ANR trace。
4. **看热点日志**：确认是否打出 `✔ 热点模式: UDP 7999 监听线程已启动`，
   以及后续有没有 `connect  packet:<IP>`。
5. **日志怎么拿**：主界面右上角「方控」左边的 **下载日志** 按钮 → 手机扫二维码
   （车机 WLAN 要与手机同网）→ 下载 `ConnLog` 全文。
