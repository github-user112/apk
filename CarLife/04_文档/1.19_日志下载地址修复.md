# 1.19 —— 「下载日志」二维码打不开的定位与修复

> 版本：`versionCode 119` / `versionName mod1.19`
> 工程：`CarLife/01_工程源码/_w119`　补丁：`02_补丁脚本/patch_v16_日志地址修复.py`
> 触发：用户反馈「日志下载的还是不行，手机端打不开你给的二维码」
> 验证环境：realme X7 Pro（RMX2121，Android 12，`adb -P 5039`）

---

## 1. 一句话结论

**二维码指向了蜂窝网卡的内网地址。** `localIps()` 把本机所有非回环 IPv4 一律收录、
不排序、不区分网卡类型，真机上枚举出的第一个就是蜂窝 `ccmni2 = 10.98.124.35`，
而它对任何对端设备都不可达 —— 扫了必然打不开。

1.19 只改「地址怎么选」，服务端、文件收集、界面框架一行没动。

---

## 2. 真机实测取证

### 2.1 网卡实况（`adb shell ip -4 addr`）

```
1:  lo      inet 127.0.0.1/8          回环
4:  ccmni2  inet 10.98.124.35/8       蜂窝数据      ifindex 4
36: ap0     inet 192.168.227.155/24   本机热点      ifindex 36
```

- **没有 `wlan0`** —— Wi-Fi 未连接（`Supplicant state: DISCONNECTED`）
- `ccmni2` 的 ifindex 是 4，`ap0` 是 36。`NetworkInterface.getNetworkInterfaces()`
  按 ifindex 返回 → **蜂窝排在热点前面**。

### 2.2 于是 1.18 生成的地址列表是

```
localIps() = [ "10.98.124.35", "192.168.227.155" ]
                ↑ 蜂窝，不可达        ↑ 热点，可达
```

`baseUrls()[0]` = `http://10.98.124.35:18080` → 第一个二维码就是它 → **打不开**。

这也解释了为什么"1.16 在 MuMu 上验证通过"：MuMu 只有一张 `eth0/192.168.1.x`，
没有蜂窝网卡，所以永远命中最前面的那张、恰好是可达的。**这个 bug 只在真机上才暴露。**

### 2.3 日志文件是有的（下载链路的数据源没问题）

```
/sdcard/Android/data/com.baidu.carlifevehicle/files/log/
    └── 2026-09-21T10:44:56.179Z.log   1,378,805 B
```

这正是 `refreshFiles()` 里 `sCtx.getExternalFilesDir(null)/log` 的落点，后缀 `.log`
也在收集白名单内。**所以本次不需要动文件收集逻辑。**

## 3. 改了什么

只动 `logxfer_src/` 下三个文件（Java 改完经 `构建日志下载smali.py` 重新产出 smali）：

### 3.1 `LogHttpServer.java`

| 改动 | 说明 |
|---|---|
| `localIps()` 重写 | ① 排除蜂窝/隧道网卡（`ccmni`/`rmnet`/`pdp`/`ppp`/`tun`/`clat`/`sit`/`dummy`…）；② 其余按可达性排序 **p2p > wlan > ap > eth > 其他**；③ 排除 `169.254.*`（link-local）与 `0.*` |
| 单网卡容错 | 1.18 是**整轮** `try/catch` —— 一张网卡抛异常会把后面所有网卡一起丢掉。改成 per-interface try/catch + 迭代器 `guard < 64` 防死循环 |
| 新增 `netSummary()` | 逐张网卡列「类别 网卡名=IP」，**被忽略的蜂窝也标出来**，供界面显示 |
| 新增私有助手 | `isUnreachableIf` / `prioOf` / `kindOf` / `firstIpv4` / `usable` / `joinIps` |

排序用**手写冒泡**（稳定），沿用原有风格，不引入 `Comparator`。

### 3.2 `LogDownloadActivity.java`

- 标题下方新增**网卡摘要行**（`netSummary()`）：现场出问题时能一眼分辨是
  「地址选错了」还是「网络根本没通」——以前只有"扫不开"三个字，无从判断。
- 提示里补上**本机自测入口** `http://127.0.0.1:18080`（同一台设备自测最可靠）。

### 3.3 `assets/logxfer/logxfer.html`

- **只给首选地址（`urls[0]`）生成一个二维码**，其余降级为小字备选列表。
  1.18 是前 3 个地址**各画一个二维码**，扫到哪个全凭运气 —— 真机上正好扫到蜂窝那张。
- 二维码尺寸 190px → 200px。

## 5. 顺带修掉的三处工具链问题（都是这次踩出来的）

### 5.1 壳 APK 里的同名类会**静默覆盖**新产物 ⚠️ 最坑

`构建日志下载smali.py` 要把「壳 APK + 追加 classes9.dex」交给 apktool 反汇编来拿 smali。
**壳里不能有同名类** —— apktool 对重复类名只保留一份。

- 1.16 时壳用的是 **1.15 的 APK**（那时还没有 logxfer 类）→ 没暴露
- 本次脚本自动挑"05_产物 里最新版"，挑到了 **1.18 成品**，而 **1.18 自己就含 logxfer**
  → 壳里的**旧版覆盖了新版**，`netSummary()` 等新方法**全没进 smali**。
  而 `build/classes/*.class` 和 `build/dex/classes.dex` 里**明明都是有的** ——
  只看"构建成功"完全看不出来。

修复：

1. `apk_contains_logxfer()` —— 逐个候选壳检查 dex 里是否含 `logxfer`，含则**硬性排除**；
2. 候选来源改为 **1.6 基线 APK 优先**（`CarLife_Direct_Fix/1-baseline-apk/`，实测不含 logxfer）；
3. 新增**方法级一致性校验**（第 7 步）：用 `javap -p` 取出每个 class 的方法名集合，
   与产出 smali 的 `.method` 集合比对，**少一个就报错退出**。
   ```
   === 方法级一致性 (smali ⊇ class) ===
     [OK]   LogHttpServer   34 个方法全在
   ```
   这道校验当场就抓出了上面的覆盖问题。

> 小坑：`javap` 把**构造器**打成全限定类名（`public com.foo.Bar();`），
> 而 smali 里是 `.method public constructor <init>()V`。解析时要把含 `.` 的名字
> 归一化成 `<init>`，否则每个类都会误报"少一个方法"。

### 5.2 中间产物目录触发沙箱"批量删除保护"

`logxfer_src/build/` 里攒了 2329 个反汇编小文件，下一轮开头的 `shutil.rmtree(BUILD)`
被安全机制拦下（一次删 2329 个 > 阈值 50）。改成 `tempfile.mkdtemp()`，
中间产物放系统临时目录，**不再需要删**，顺带也彻底不污染仓库。

### 5.3 `校验并补齐工程.py` 的期望清单补登

本次内容差异 5 处，其中两处（`assets/logxfer/logxfer.html`、
`LogDownloadActivity$BackHandler.smali`）是新登记的：
**外层类一改，内部类 `$BackHandler` / `$1` 的 smali 会跟着变**，这是正常的，
以后凡是改 logxfer 都会出现，所以连 `qrcode.js` / `LogXferEntry*` 一并登记。
