# 1.20 —— 修 1.18 插桩引入的 VerifyError（真机崩溃）

> 版本：`versionCode 120` / `versionName mod1.20`
> 工程：`CarLife/01_工程源码/_w120`　补丁：`02_补丁脚本/patch_v17_修插桩VerifyError.py`
> 前置：1.19（日志下载地址修复）—— 1.20 = 1.19 + 本修复
> 验证环境：realme X7 Pro（RMX2121，Android 12）

---

## 1. 症状

1.20 的起因是在真机上验 1.19 时发现的：**app 一启动就崩**，主界面刚出来就被系统强杀。

```
FATAL EXCEPTION: main
Process: com.baidu.carlifevehicle
java.lang.VerifyError: Verifier rejected class a.a.a.a.m.m.d.a:
  void a.a.a.a.m.m.d.a.run() failed to verify:
  [0x147] Invalid reg type for array index (Reference: java.lang.Object[])
    at a.a.a.a.m.m.d.d$c.run(:5)
```

`a.a.a.a.m.m.d.a` 是**蓝牙带外握手（阶段 1）**那个 Runnable
（`d/d$c` 是包装它、用完往 Handler 上 post 的那个）。
**类被 verifier 直接拒绝 → 一执行就炸。**

---

## 2. 根因：1.18 的两处插桩缺陷

### 2.1 数组索引寄存器的类型在合并点不一致

1.18（`patch_v15`）在蓝牙/热点阶段插日志，用的是**四件套**写法：

```smali
const/4 v12, 0x1
new-array v12, v12, [Ljava/lang/Object;
const/4 v13, 0x0
const-string v14, "日志文本"
aput-object v14, v12, v13        # ← 第三个操作数是数组索引, 必须是整数
invoke-static {v7, v12}, La/a/a/a/n/g$a;->a(...)
```

问题出在 **1.2 / 1.3 两处没写 `const/4`，直接复用了 `v3` 当索引**：

```smali
    :goto_5
    if-nez v0, :bt_have_target
    ...
    aput-object v14, v12, v3      # ← v3 在这里来自上游, 类型不定
    ...
    :bt_have_target               # ← 两条路径在这里汇合
```

`d/a.run()` 里 **v3 被用了 29 次**，中间的原代码早把它改成了引用类型；
到 `:bt_have_target` 合并点时，v3 一路是"整数"、一路是"引用" →
**verifier 判定类型冲突，拒绝整个类**。

### 2.2 1.5 处把「1 秒后重试」的控制流写坏了

原代码（`_w117` 干净基线）语义是：

```smali
:cond_1a
... isEmpty / xor 1 → v0（列表是否非空）
if-eqz v0, :cond_1b          # 列表非空 → 结束
iget-boolean v0, ...->h:Z    # h：是否"已全失败一轮"
if-eqz v0, :cond_1b          # h==0 → 结束
:goto_14                     # 否则 1 秒后重试
```

1.18 改成了：

```smali
if-eqz v0, :bt_all_failed
:bt_all_failed               # ← 紧跟 if，等于两条路径都落进来
<打"全部连不上"日志>
goto :cond_1b                # ← 把 :goto_14 的 1 秒重试整个跳过了
```

后果有两个：
1. `h==0`（没全失败）也会打出「已配对设备全部连不上」的**误报日志**；
2. **原有的 1 秒重试被彻底跳过** —— 这是功能回归，不只是日志问题。

## 3. 为什么前几版都没发现

| 环境 | Dalvik/ART | 结果 |
|---|---|---|
| 车机 Android 4.4.2 | **Dalvik** | 校验宽松，不报 → 照常跑 |
| MuMu Android 4.4.4 | **Dalvik** | 同上 → 1.18 的冒烟测试全过 |
| realme 真机 Android 12 | **ART** | 严格校验 → **直接拒类** |

**这是"用模拟器验 smali 补丁"的典型盲区**：Dalvik 能容忍的类型不一致，
ART 会直接拒绝加载。凡是新写/改动的 smali 类，**都必须过一遍 ART**。

---

## 4. 修法：插桩不再碰任何局部寄存器

在别人的大方法里"小心翼翼地挑一个没被占用的寄存器"本身就是错的方向。
1.20 改成**零参静态方法**：

在 `ConnLog`（我们自己写的类）里加：

```smali
.method public static logLine(Ljava/lang/String;)V     # 公共实现，寄存器自控
    .locals 4
    const/4 v0, 0x1
    new-array v0, v0, [Ljava/lang/Object;
    const/4 v1, 0x0
    aput-object p0, v0, v1
    const-string v2, "CarLife_SDK"
    invoke-static {v2, v0}, La/a/a/a/n/g$a;->a(Ljava/lang/String;[Ljava/lang/Object;)V
    return-void
.end method

.method public static logBtNoTarget()V                # 9 个零参包装之一
    .locals 1
    const-string v0, "⚠ [蓝牙] 未找到名为 CONFIG_TARGET_BLUETOOTH_NAME 的已配对设备, 跳过握手"
    invoke-static {v0}, Lcom/baidu/carlifevehicle/ConnLog;->logLine(Ljava/lang/String;)V
    return-void
.end method
```

插桩点于是变成**一行**：

```smali
invoke-static {}, Lcom/baidu/carlifevehicle/ConnLog;->logBtNoTarget()V
```

- **零寄存器操作数** → verifier 无从挑剔，`aput-object` 的索引风险从根上消失
- 新方法 `.locals` 自己声明，寄存器完全自洽
- 字符串与方法体都集中在 `ConnLog`，**下一版改文案不用再动别人的方法**

同时把 2.2 的控制流改回原语义：

```smali
:bt_have_bonded
iget-boolean v0, v2, ...->h:Z
if-nez v0, :cond_1b                                    # h==0 → 结束（原语义）
invoke-static {}, Lcom/baidu/carlifevehicle/ConnLog;->logBtAllFailed()V
:goto_14                                               # h!=0 → 落到 1 秒重试（原语义）
```

## 6. 自检里用到的"基线回归"手法

插桩清干净没有，**不能靠"看着像"**。这次的做法是拿干净基线（`_w117`）当参照，
比对两个可直接计数的指标：

| 文件 | 指标 | `_w117` 基线 | 1.18/1.19（脏） | 1.20（修后） |
|---|---|---|---|---|
| `d/a` | `aput-object` 处数 | **15** | 21 | **15** ✓ |
| `d/a` | `n/g$a` 静态日志调用 | **0** | 6 | **0** ✓ |
| `e/a` | `aput-object` 处数 | **4** | 7 | **4** ✓ |
| `e/a` | `n/g$a` 静态日志调用 | **1** | 4 | **1** ✓ |

`n/g$a` 计数回到基线，是"6 处插桩全部转成零参、无残留"的最强证据。

> ⚠ 小坑：别用裸 `str.count()` 数这些指标 —— 补丁的**注释里**会写
> "不再 `new-array`/`aput-object`" 这类字样，会把注释一起数进去
> （`d/a` 的 aput-object 就被数成 16 而不是 15）。要**排除以 `#` 开头的行**再统计。

## 7. 验收结果

### 7.1 崩溃已消除 ✅

装机 `versionCode=120` / `versionName=mod1.20` 后：

| # | 项目 | 结果 |
|---|---|---|
| 1 | 启动 | `mCurrentFocus=Window{… com.baidu.carlifevehicle/.CarlifeActivity}`，**主界面正常显示** |

| 4 | 零参插桩生效 | 日志区打出 `==== [阶段1] 蓝牙带外握手: 开始扫描/连接手机 ====` |

对照：1.19 在同一台机器上**一启动就崩**，本版修好。

## 8. 这一版留下的最大教训

| 环境 | Dalvik/ART | 1.18 的插桩缺陷 |
|---|---|---|
| 车机 Android 4.4.2 / MuMu 4.4.4 | Dalvik | **测不出来** |
| realme Android 12 | ART | 一启动就崩 |

**「模拟器全过」不等于「能装真机」。** 以后凡是新写/改动的 smali 类，
必须至少在一台 ART 设备上跑一遍启动 —— 这是唯一能发现寄存器类型冲突的手段。
`verify_dalvik_合并点检查.py` 是静态近似，能拦掉一部分，但不能替代真机。
