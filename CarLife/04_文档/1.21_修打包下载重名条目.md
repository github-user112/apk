## 1. 症状

1.20 在真机上验证时，「下载日志」页本身已经正常了（二维码地址对、列表页能开、
单文件能下），但**点「打包下载全部」直接失败**：

```
CarLifeLogXfer: REQ /all.zip
CarLifeLogXfer: handle: java.util.zip.ZipException: duplicate entry:
                2026-09-21T10:44:56.179Z.log
```

curl 侧表现为 `exit 52`（empty reply）/ HTTP 000 —— 服务端在写响应头**之前**就抛了。

---

## 2. 根因：同一份文件被收了两遍

`LogHttpServer.refreshFiles()` 一次性登记了 6 个候选目录：

```java
dirs.add(new File(getFilesDir(), "log"));            // /data/user/0/<pkg>/files/log
dirs.add(new File(getExternalFilesDir(null), "log")); // /storage/emulated/0/Android/data/<pkg>/files/log
dirs.add(getExternalFilesDir(null));                  // /storage/emulated/0/Android/data/<pkg>/files
dirs.add(new File("/sdcard/BaiduCarlife"));
dirs.add(new File("/sdcard/Android/data/<pkg>/files/log"));
dirs.add(new File("/storage/sdcard0/BaiduCarlife"));
```

第 2 项和第 5 项**指向同一个目录** —— Android 上 `/sdcard` 与
`/storage/sdcard0` 都是 `/storage/emulated/0` 的**符号链接**。

而当时的去重键是：

```java
String p = f.getAbsolutePath();     // ← 两种写法字符串不同
if (mSeen.contains(p)) { continue; }
```

于是同一个日志文件：

| 来源目录 | 收进来的绝对路径 |
|---|---|
| `getExternalFilesDir(null)/log` | `/storage/emulated/0/Android/data/…/files/log/x.log` |
| `/sdcard/Android/data/…/files/log` | `/sdcard/Android/data/…/files/log/x.log` |

**字符串不同 → 去重失效 → `mFiles` 里同一文件两份** →
`sendZip()` 的 `ZipOutputStream` 遇到重名条目 → `ZipException`。

> 真机日志里的铁证（1.20）：
> ```
> dir missing: /data/user/0/com.baidu.carlifevehicle/files/log
> dir missing: /sdcard/BaiduCarlife
> dir missing: /storage/sdcard0/BaiduCarlife
> refreshFiles count=2 -> …/files/log/x.log;     ← 同一文件, 两种路径
> ```
> 6 个目录里 3 个不存在，剩下的 3 个中两个是同一个 —— 所以 2 条记录其实是 1 个文件。

**注意**：列表页（`/`）和单文件下载（`/f/<idx>`）不受影响，因为前者只显示计数、
后者按下标取文件。只有 zip 会因为重名条目整包失败。

## 3. 修法：两个静态助手

### 3.1 `canonicalKey(File)` —— 去重键改用规范路径

```java
private static String canonicalKey(File f) {
    try {
        String c = f.getCanonicalPath();      // 真正解开符号链接
        if (c != null && c.length() > 0) { return c.replace('\\', '/'); }
    } catch (Throwable ignored) { }
    String p = f.getAbsolutePath().replace('\\', '/');
    // 某些精简 ROM 上 getCanonicalPath 会失败/不解析, 手工归一化别名前缀
    if (p.startsWith("/sdcard/"))            p = "/storage/emulated/0/" + p.substring("/sdcard/".length());
    else if (p.startsWith("/mnt/sdcard/"))   p = "/storage/emulated/0/" + p.substring("/mnt/sdcard/".length());
    else if (p.startsWith("/storage/sdcard0/")) p = "/storage/emulated/0/" + p.substring("/storage/sdcard0/".length());
    return p;
}
```

- 优先 `getCanonicalPath()`：真机上它把 `/sdcard/…` 解析成 `/storage/emulated/0/…`，
  两条记录自然合并成一条
- 退回路径里用 `substring("前缀".length())` 而不是硬编码下标 —— 前缀改了不会算错

### 3.2 `uniqueName(List, String)` —— 条目名兜底唯一

即使去重做对了，**不同目录下仍可能有同名日志**。zip 不允许重名条目（解压端也会报错），
所以冲突时补 `_2` / `_3` 后缀，扩展名挪到最后：

```java
private static String uniqueName(List used, String name) {
    if (name == null || name.length() == 0) { name = "log"; }
    if (!used.contains(name)) { used.add(name); return name; }
    String base = name, ext = "";
    int dot = name.lastIndexOf('.');
    if (dot > 0 && dot < name.length() - 1) { base = name.substring(0, dot); ext = name.substring(dot); }
    for (int i = 2; i < 100000; i++) {
        String cand = base + "_" + i + ext;
        if (!used.contains(cand)) { used.add(cand); return cand; }
    }
    return base + "_" + System.currentTimeMillis() + ext;   // 理论兜底, 不会走到
}
```

调用点两处：

```java
// refreshFiles()
String p = canonicalKey(f);
if (mSeen.contains(p)) { continue; }

// sendZip()
List used = new ArrayList();
zos.putNextEntry(new ZipEntry(uniqueName(used, f.getName())));
```

### 6.1 额外造的「同名文件」场景

真机上日志目录只有 1 个文件，`uniqueName()` 的分支没被覆盖。于是在**另一个也被登记的目录**
（`…/files/`，即 `getExternalFilesDir(null)` 本身）放了一个**同名**文件：

```
/storage/emulated/0/Android/data/<pkg>/files/2026-09-21T10:44:56.179Z.log       15 字节  ← 人造
/storage/emulated/0/Android/data/<pkg>/files/log/2026-09-21T10:44:56.179Z.log   1415510 字节 ← 真日志
```

结果（`count=2`，两个不同 canonical 路径都保留，**去重没有误杀不同文件**）：

```
条目数: 2
重名条目: (无)
  2026-09-21T10:44:56.179Z.log        15 ->       15 bytes   ← 内容 b'TEST_SAME_NAME\n'
  2026-09-21T10:44:56.179Z_2.log   91911 ->  1415510 bytes   ← 真日志
CRC: OK
```

`uniqueName()` 把第二个改名成 `_2.log`，两个文件内容各自正确。测完已删除，恢复 `count=1`。

> 这一步同时证明了 `canonicalKey` 的两面：**同一文件的不同别名被合并**、
> **不同文件不会被误合并**。只验前一面是不完整的。
