## 1. 症状（车机 4.4.2 实测）

直连（WiFi Direct）模式下，界面日志区打出：

```
【蓝牙】蓝牙未开启，跳过蓝牙通道
```

但车机系统里蓝牙**已经连上手机**。之后 P2P 组能建起来，手机却不会来 join，
表现为「组网成功但进不去」。

## 2. 定位：这句话是谁打的、什么条件下才打

界面上的中文是 `res/values/arrays.xml` 里我们自己加的 `cl_log_keys / cl_log_vals`
映射表翻译出来的，原 SDK 日志是：

```
bluetoothAdapter?.isEnabled: false, so return
```

打这条日志的**唯一**位置：`smali/a/a/a/a/m/m/d/a.smali`（`d$a.run()`，
阶段 1 蓝牙带外握手的 Runnable）。读汇编得到判定链：

| 条件 | 结果 |
|---|---|
| `d.b()` 返回 null | **不**走这条（Kotlin `bluetoothAdapter?.isEnabled == false` 对 null 不成立） |
| `d.b()` 非 null 且 `isEnabled() == true` | 继续走握手（getBondedDevices → SPP） |
| `d.b()` 非 null 且 `isEnabled() == false` | **打这条日志 + 直接 return**，蓝牙通道整条被跳过 |

`d.b()` 的实现在 `smali/a/a/a/a/m/m/d/d$b.smali`：
`context.getSystemService("bluetooth") -> BluetoothManager.getAdapter()`（API 18+）。

所以结论是明确的：**CarLife 拿到了适配器，但 Android 标准 API 报告它是 OFF 的。**
不是「读不到蓝牙信息」，是「读到的状态是关」。

## 3. 车机上为什么会出现「实际能用 / API 报 OFF」

只有三种可能：

| # | 根因 | 特征 |
|---|---|---|
| A | **时序**：App 启动时蓝牙还在 `STATE_TURNING_ON`（isEnabled 仍 false） | 稍后再查就是 ON；1.18 加的 `STATE_ON` 广播重试只在「enable() 真的触发了一次开机广播」时才激活，蓝牙本来就 ON 或 ROM 不发广播时这条自愈链路**根本不会启动** → 一次判死 |
| B | **ROM 双蓝牙**：车机蓝牙电话/音乐走 MCU，Android 侧 BluetoothAdapter 长期 OFF | 永远等不到 ON，任何重试都无效 |
| C | **状态不同步**：`BluetoothManager.getAdapter()` 与 `BluetoothAdapter.getDefaultAdapter()` 结论不一致 | 两条路径一个说 OFF 一个说 ON |

1.22 之前无法区分 A / B / C，因为日志只有一句"未开启"。

## 4. 怎么修的

### 4.1 新增 `BtGuard`（Java → smali，走 logxfer 的既有构建链）

`com.baidu.carlifevehicle.logxfer.BtGuard.onSkipDecision(boolean skip, Runnable target)`：

| 情形 | 行为 |
|---|---|
| 蓝牙已开启（skip=false） | 返回 false，继续握手；等待计数清零，并打 `✔ [蓝牙] 已开启, 继续带外握手` |
| `getDefaultAdapter()` 为 null | 真·无蓝牙硬件 → `✖ [蓝牙] 系统无蓝牙适配器, 放弃蓝牙通道` |
| 未开启 | 每秒重试一次，**最多 30 次**；每次顺手 `enable()`；进度打进界面日志区：`… [蓝牙] 未开启, 第 N/30 次等待(1s 后重试, 已请求 enable)` |
| 30 次仍 OFF | `✖ [蓝牙] 已等待 30s 仍未开启, 放弃蓝牙通道(请检查车机蓝牙)`，行为退回 1.21 |
| 两条获取路径结论不一致 | 单独打 `⚠ [蓝牙] 状态不一致: BluetoothManager.getAdapter()=off / getDefaultAdapter()=on` → **一眼区分情况 C** |

日志通过反射调 `ConnLog.logLine(String)`（拿不到就退回 `android.util.Log`），
所以能在车机界面日志区直接看到，也能进 1.16 起的「下载日志」导出文件。

### 4.2 重试为什么走工作线程

`d$a` 本来就是 `ExecutorService.execute()` 丢进线程池跑的，
后面的 SPP `connect()` 是**阻塞调用**。所以 BtGuard 用
`ScheduledExecutorService`（守护线程 `CarLifeBtWait`）重跑 `run()`，
**不碰主线程** —— 上主线程会 ANR。

### 4.3 插桩点（一行，两个现成寄存器）

在 `d/a.smali` 的 `:goto_1`（v0 = 原"是否跳过"结论已确定）之后：

```smali
    invoke-static {v0, v1}, Lcom/baidu/carlifevehicle/logxfer/BtGuard;->onSkipDecision(ZLjava/lang/Runnable;)Z
    move-result v0
```

- `v0` = 原结论；返回值写回 `v0`，语义不变
- `v1` = `this`（`d$a` 实现了 `Runnable`，重试时原样重跑，含全部既有插桩日志）
- **不新占寄存器、不动任何既有分支** —— 遵守「血泪 12：插桩一律走静态方法」

## 6. 车机上怎么验证

1. 装 1.22，进直连模式，看界面日志区：
   - 出现 `… [蓝牙] 未开启, 第 1/30 次等待…` 且数字递增 → **情况 A（时序）**，等它涨到某次后会出现 `✔ [蓝牙] 已开启, 继续带外握手` 并往下走握手 → **问题解决**
   - 出现 `⚠ [蓝牙] 状态不一致` → **情况 C**，下一步改 `d$b`（把获取适配器的路径换成 `getDefaultAdapter()` 兜底）
   - 一路涨到 30 后 `✖ 已等待 30s 仍未开启` → **情况 B（MCU 蓝牙）**，App 层无解，请改走热点模式绕开蓝牙带外
2. 点「下载日志」导出的文件里有 `====== 蓝牙信息 ======` 段（`InfoDump.dumpBluetooth()`），
   能看到 `蓝牙: 已开启/已关闭`、蓝牙名、MAC、已配对设备数 —— 与上面的日志交叉验证。
3. adb 侧（有 adb 时）：
   ```
   adb shell settings get global bluetooth_on
   adb logcat -v time | grep -i "bluetoothAdapter\|BtGuard\|CarLife_SDK"
   ```

## 7. 已知边界

- 1.22 **不解决情况 B**（ROM 蓝牙不走 Android 栈），只把它明确暴露出来。
- 等待上限 30 次 × 1s = 30s；超时后行为与 1.21 完全一致（跳过蓝牙通道），不会更差。
- 每次等待都会调一次 `enable()`；需要 `BLUETOOTH_ADMIN`（Manifest 里已有）。
