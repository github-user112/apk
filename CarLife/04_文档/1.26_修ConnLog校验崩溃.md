## 1. 现象

MuMu 上装 1.25，`monkey` 拉起 `CarlifeActivity` 后立刻崩溃：

```
W/dalvikvm( 2427): VFY: invalid use of move-exception
W/dalvikvm( 2427): Verifier rejected class Lcom/baidu/carlifevehicle/ConnLog;
D/AndroidRuntime( 2427): Shutting down VM
E/AndroidRuntime( 2427): FATAL EXCEPTION: main
E/AndroidRuntime( 2427): java.lang.VerifyError: com/baidu/carlifevehicle/ConnLog
E/AndroidRuntime( 2427): 	at a.a.a.a.n.g.c(:8)
E/AndroidRuntime( 2427): 	at a.a.a.a.a.e.y(:3)
E/AndroidRuntime( 2427): 	at a.a.a.a.m.d.<init>(:11)
E/AndroidRuntime( 2427): 	at com.baidu.carlifevehicle.VehicleApplication.onCreate()
```

崩溃点在 `VehicleApplication.onCreate()` → SDK 日志器初始化 → `ConnLog`。
`ConnLog` 是 1.16 引入的**我方日志桥接类**，它一被拒类整个进程就起不来。

---

## 2. 根因：1.25 新增的三个方法 try/catch 结构全写坏

1.25 在 `ConnLog.smali` 里新增了 `precheck()` / `hasUsableLocalIp()` / `awaitLocalIp()`，
三个方法都带 try/catch，写法全部不合规。

### 2.1 致命：`hasUsableLocalIp()` 把「循环退出」跳进了 catch handler

```smali
    :goto_0
    if-eqz v1, :catch_0        # ← 枚举为 null，退出循环
    invoke-interface {v1}, Ljava/util/Enumeration;->hasMoreElements()Z
    move-result v3
    if-eqz v3, :catch_0        # ← 没有更多元素，退出循环
    ...
    if-ge v2, v3, :catch_0     # ← 超过 64 个，退出循环
    ...
    :catch_0
    move-exception v4          # ← handler 首指令
```

`:catch_0` 是**异常处理器入口**，它的第一条指令必须是 `move-exception`，
且只能由异常到达。上面三条是**正常控制流**跳过去的 —— 一旦走这条路，就会在
没有异常的状态下执行 `move-exception`，Dalvik verifier 直接报
`invalid use of move-exception` 并**拒掉整个类**。

> 这就是血泪第 11 条的又一次兑现，而且是反方向：
> 上次是「Dalvik 宽松、ART 拒类」，这次是 **Dalvik 直接拒类**（ART 上大概率同样拒）。

### 2.2 `precheck()` / `awaitLocalIp()`：正常出口落在 handler 区之后

```smali
    :try_end_0
    .catch Ljava/lang/Throwable; {:try_start_0 .. :try_end_0} :catch_0

    goto :done          # 正常路径跳 :done

    :catch_0
    move-exception v0

    :done               # ← 位于 handler 区内，正常分支跳进来了
    return-void
```

handler 块从 `:catch_0` 一直延伸到方法结束，`:done` 在里面；
正常分支跳进 handler 区域属于同一类违规。

### 2.3 附带查出：一处极性写反

```smali
    invoke-virtual {v4}, Ljava/lang/String;->length()I
    move-result v5
    if-nez v5, :goto_1     # ✗ 长度非 0 时反而跳过该地址
```

本意是「空串地址跳过」，应 `if-eqz`（v5==0 才跳）。已修。
（同一个方法里 `isLoopback` / `isLoopbackAddress` / 两个 `startsWith` 的极性是**对的**，
排查时反复确认过，不要顺手改回去。）

---

## 3. 修法（最小改动，不动业务逻辑）

统一成一条规则：**正常出口的标签一律放在 `:catch_0` 之前，handler 独占并挪到方法末尾。**

| 方法 | 改动 |
|---|---|
| `precheck()` | 删掉 `goto :done`，`:done` 提到 `:catch_0` 之前；handler 自己 `return-void` |
| `hasUsableLocalIp()` | 三条循环退出 `:catch_0` → `:ret`；`:ret` 提到 handler 之前；handler 里 `const/4 v0, 0x0` + `return v0` |
| `awaitLocalIp()` | 删掉 `goto :tick`，sleep 后顺序落到 `:tick`；handler 挪到方法末尾，处理完 `goto :tick` |

修改后的方法骨架：

```smali
    :try_start_0
    ...
    :try_end_0
    .catch Ljava/lang/Throwable; {:try_start_0 .. :try_end_0} :catch_0

    :ret            # 正常出口 —— 必须在 handler 之前
    return v0

    :catch_0        # 只由异常到达，独占方法末尾
    move-exception v4
    const/4 v0, 0x0
    return v0
.end method
```

补丁脚本 `patch_v23_修ConnLog校验与极性.py` 用 `sub_once()` 做**精确替换**，
匹配次数不是 1 就直接报错退出 —— 防止补丁静默失效（血泪：静默失效比报错贵得多）。
脚本末尾还带一道自检：方法体内不允许再有非 handler 的分支跳 `:catch_x`。

另外全仓扫了一遍 `smali/`，没有其它「正常分支跳 catch 标签」的地方。

### 4.3 一个待复核的疑点

MuMu 上 `netcfg` 显示 `eth0 UP 10.0.2.15`、`eth1 UP 10.0.3.15` 都是合法 IPv4，
但 `hasUsableLocalIp()` 仍返回 false（所以打了「IP 超时」）。
最可能的原因是 QEMU 环境下 `NetworkInterface.getNetworkInterfaces()` 返回 null
或抛 `SocketException`，走了兜底 return 0。

- 影响面：**不阻断**，只多等 5 秒 + 多一条提示。
- 待办：车机/真机上确认能打出 `✔ 网卡 IP 已就绪 (waited 0ms)`；
  若真机也恒超时，就在 `hasUsableLocalIp()` 的 catch 里补一条异常日志定位。
