# CarLife 车机端 vs 亿连 V7.0.1 —— 三链路对比审计 & 1.11 加固说明

> 审计对象：`com.baidu.carlifevehicle` CarLife 4.0 车机端（个人修改版 1.10 → 本次 1.11）
> 参照对象：`net.easyconn` 亿连手机互联 V7.0.1（minSdk 16 / targetSdk 28，与 CarLife 同为 Android 4 兼容）
> 日期：2026-09-22

---

## 0. 一句话结论

1.10 的直连**链路能跑起来了，但"断了不会自己好、失败不会分级、手机找不到车机"**三件事没解决，
而且它为了止住 `discoverPeers` 风暴把发现整个抑制掉，**副作用是组一旦丢失就彻底静止**。
1.11 针对这三点做了加固，并顺手把热点（缺组播锁）和 USB（每秒弹权限窗）两个长期顽疾一起修了。

## 1. 先说 1.10 的直连：审下来有哪些问题

1.10 已经打进去的补丁（基线 `_w110`）：

| 补丁 | 内容 | 状态 |
|---|---|---|
| A | `assets/bdcf` 加 `CONFIG_WIFI_DIRECT_NAME=CarLife-HU`；`CONFIG_WIRLESS_FREQUENCY` 5G→2.4G | ✅ |
| B | 蓝牙未开时 `enable()` 并置 `d.h=true` | ✅ |
| C | `WifiP2pManager.setDeviceName` 同步配置的直连名（仅 API<29） | ✅ |
| D | 新增自举器 `d/j`：8 秒没组就自己 `createGroup()` 当 GO | ✅ |
| E | 断开清理：`cancelConnect` + `removeGroup` + `stopPeerDiscovery` | ✅ |
| F | 停掉每秒 `discoverPeers` 循环；建组前先 `stopPeerDiscovery` | ✅ |
| G | `d/b.smali` 把 `discoverPeers` 改成只打日志不再调 | ✅ |

审计发现的**缺口**：

1. **断了不会自愈（最严重）**
   `d/i.smali` 的 `onReceive` 在 `info==null` 或 `groupFormed==false` 时走 `:cond_5`，
   那里调用 `h.c.a()` 想重启发现——但 patchG 已经把 `discoverPeers` 变成空操作。
   结果：**组一旦丢失，链路彻底静止，只能重启 App。**
2. **失败不分级**　`createGroup` 的 `onFailure(reason)` 一律 8 秒重试。
   `reason=1`（驱动不支持）和 `reason=2`（BUSY）完全不同的性质，却同样重试 6 次。
3. **48 秒后永久死**　6 次 × 8 秒耗尽就放弃，之后再也不试。车机是常电设备，这个策略太保守。
4. **手机找不到车机**　没有 DNS-SD 本地服务，只能靠蓝牙带外把 P2P 名递过去。蓝牙在车机上是最不稳的一环。
5. **组播锁是引用计数的**　亿连全程用 `setReferenceCounted(false)`，CarLife 只在自举器里 acquire 一次且默认引用计数。
6. **发现循环会被重新排上**　patchF-1 只取消一次；之后 `h.onFailure` 再被调用就会重新排 1 秒循环，
   **实测每秒一条 `discoverPeers suppressed`，P2P 状态机又被占住，`createGroup` 继续 BUSY。**

## 2. 三链路逐项对比

### 2.1 WiFi Direct（直连）

| 维度 | 亿连 | CarLife 1.10 | CarLife 1.11 |
|---|---|---|---|
| 建组主动方 | `addLocalService` → `discoverPeers` → **立刻 `createGroup`** 链式推进 | 8 秒后没组才试 | 保留 8s 窗口（等手机先建），但失败后分级重试 |
| 服务发现 | DNS-SD `EC_MIRROR / _presence._tcp`，txt 带 huid/huname/port | ❌ 无 | ✅ 新增 `CarLife-HU / _presence._tcp` |
| 连接判定 | `NetworkInfo.isConnected()` | `WifiP2pInfo.groupFormed` | 沿用 + 组丢失触发自愈 |
| 断线自愈 | `clearLocalServices` → `onSuccess` → 重新 `addLocalService`，**闭环** | ❌ 静止 | ✅ 新增 `d/k`，重新 arm 自举器（15s 去抖） |
| 失败分级 | 各回调分别打日志，BUSY 走 `removeGroup` | ❌ 不分级 | ✅ reason=1 放弃降级 / reason=2 先 removeGroup |
| 重试节奏 | 120s 固定重扫 | 6×8s 后放弃 | 快试 6 次退避 4→14s，再慢扫 12 轮 ×30s（约 7 分钟） |
| 心跳 | socket `:10922`，`setSoTimeout(3000)`，2s 一次，失败 3 次判离线 | ❌ 无 | 未做（改动面太大，列为后续） |
| 组播锁 | `setReferenceCounted(false)` 全程持有 | 引用计数，仅自举器 | ✅ 改为非引用计数 |
| 清理 | `clearLocalServices`+`stopPeerDiscovery`+`removeGroup` 三连 | `cancelConnect`+2 项 | ✅ 补齐 `clearLocalServices` |
| 发现风暴 | 无 | 每秒一次 | ✅ patchF-3 永久抑制重排 |

### 2.2 热点（不区分"手机开热点"还是"车机开热点"）

亿连的做法值得单独说一句：**它压根不关心 AP 是谁开的**。
`ecsdk/WifiManager.d()` 只做一件事——循环 `Thread.sleep(500)` 轮询，直到出现一个"合法 IP"
（正则排掉 `0.0.0.0`），然后按接口白名单给每个合法地址建一个 JmDNS 注册 `_EasyConn._tcp.local.`。
这个设计天然同时覆盖了"手机开热点车机连"和"车机开热点手机连"两种拓扑。

| 维度 | 亿连 | CarLife 1.10 | CarLife 1.11 |
|---|---|---|---|
| 拓扑 | 不区分，只看"哪个网卡有合法 IP" | 模式 5，同样是"有 IP 就能跑" | 同 |
| 传输 | JmDNS + TCP/UDP（端口由 `native_getLocalServiceInfo` 下发） | `WirlessProtocolTransport` UDP `0x1f3f` = **7999** | 同 |
| 组播锁 | ✅ 全程持有（非引用计数），关闭时 release | ❌ 完全没有 | ✅ 新增 `e/e`，进传输 acquire、终止 release |
| IP 就绪等待 | 轮询 500ms 直到拿到合法 IP | ❌ 无 | 未做（列为后续） |
| 多网卡 | 遍历 `NetworkInterface` 按白名单逐个注册 | ❌ 单地址 | 未做 |
| 关闭清理 | release 锁 + `removeServiceListener` + `close()` 全部 JmDNS | 关 socket | 同 + 释放锁 |

> 直连模式最终也要走 `WirlessProtocolTransport` 这个 UDP 通道，所以**组播锁这一项同时惠及直连和热点**。

### 2.3 USB 有线

| 维度 | 亿连 | CarLife 1.10 | CarLife 1.11 |
|---|---|---|---|
| 角色 | USB Host（AOA 主机），`device_filter.xml` 68 个 vendor-id | USB Host，有 `accessory_filter.xml`（Baidu/CarLife） | 同 |
| 设备判定 | MassStorage 跳过；VID 0x05AC=iOS；VID 0x18D1 PID 0x2D00/0x2D01=AOA；class=255/sub=66/proto=1=ADB | 同样判 MassStorage（class=8/sub=6/proto=0x50） | 同 |
| 传输类型 | `ECTransportType` 14 种（ADB=0 / AOA=1 / WIFI=2 / iOS_MUX=4 …） | `CONNECT_TYPE_ANDROID` 0=ADB 1=AOA；iPhone 0=NCM 1=Wifi | 同 |
| **权限弹窗** | 静态 `isPermissionRequesting` 防重入；后台不弹；镜像中不弹 | ❌ **每秒 `startActivity(UsbPermissionProxyActivity)`** | ✅ 新增 `c/f`，5 秒去抖 |
| 扫描节奏 | 开设备前 `sleep(100)`；iPhone 用 500ms Timer 重试并用布尔位防抖 | 固定 `sleep(1000)` 无限循环，无退避 | ✅ 被抑制时额外 sleep 4s（等效 5s 一轮） |
| 端口 | ADB 走 **5039**（避开 5037）；netshare 31338/10923/8053/10924/10922 | 沿用系统 | 同 |
| 网关 | 写死 `172.16.1.1`，退出时 `iptables -t nat -F` + 删路由 + `kill -9` | 无 | 同 |

## 4. Android 4 兼容性

亿连 `minSdkVersion: 16`；CarLife `minSdkVersion: 16 / targetSdkVersion: 30`，本次**未改动 minSdk**。

新增代码用到的 API 全部 ≤ 16：

| API | 引入版本 |
|---|---|
| `WifiP2pManager.addLocalService` / `clearLocalServices` | 16 |
| `WifiP2pDnsSdServiceInfo.newInstance` | 16 |
| `WifiManager.createMulticastLock` / `setReferenceCounted` / `acquire` / `release` | 1 |
| `SystemClock.uptimeMillis` | 1 |
| `Handler.postDelayed` / `removeCallbacks` | 1 |

未使用 lambda、try-with-resources、Java 8 时间/流式 API；smali 寄存器严格限制在 v0–v15。
另外写了 `02_补丁脚本/verify_dalvik_合并点检查.py` 专门查 Dalvik 最容易崩的
**"汇合点寄存器类型不一致"**（32 个方法全部通过）——这是造 App 时踩过的坑，4.4 上必现闪退。

## 6. 还没做的（按优先级）

1. **心跳探活**（亿连最强的一点）：直连建组成功后周期性探测对端 IP:端口，
   连续 2 次失败判离线并触发自愈。目前断线只能靠 `CONNECTION_STATE_CHANGE` 广播，
   广播丢失就没救了。
2. **热点侧 IP 就绪等待**：照抄亿连 `publishMdns` 的 500ms 轮询 + 合法 IP 正则，
   避免"网卡还没拿到 IP 就开始发握手包"。
3. **多网卡遍历**：车机常有多个接口（wlan0 / p2p0 / usb0 / eth0），按白名单逐个尝试。
4. `CONFIG_HU_BT_NAME` / `CONFIG_HU_BT_MAC` 仍是占位符 `xxx` / `yyy-zzz-xxx`，**待填车机真实蓝牙名与 MAC**。
5. 有线模式独立 bug：`UsbAccessoryScanner` 拿不到权限时仍会一直扫；模式被记住会锁死在有线。
6. MuMu 模拟器已不在本机，Android 4.4 真机/车机实跑仍未验证——建议上车机先看界面自检四行。
