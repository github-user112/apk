## 0. 结论速览

1. **亿连是"薄 Java 门面 + 巨型 native 核心"架构**：Java 侧 `ECSDK` 单类 263 个方法，其中 **130+ 个是 `native_` JNI 入口**，真正协议栈在 `lib/` 下的 **libECSDK.so（8 MB）**。Java 层基本只做参数打包 + 回调分发。
2. **传输层抽象成一个枚举 15 种**（`ECTypes.ECTransportType`）：Android 的 USB-AOA / USB-ADB / WiFi / BT-RFCOMM / BLE / BLE_ENCRYPT / MIRACAST，iOS 的 USB-AirPlay / USB-EAP / USB-Lightning / USB-MUX(usbmuxd) / WiFi-AirPlay / WiFi-APP，加 DLNA，`MAX` 收尾。
3. **连接核心是混淆类 `f.a.i.i.q`**：73 方法 / 55 字段，持有 `WifiP2pDevice`、`UsbDevice`、`NetLinkService`，是 **Handler 消息状态机**；`openTransport` 的唯一调用者就是它的内部 `d.handleMessage`。
4. **WiFi Direct 的封装在 `EcWifiManager`**（持有 `WifiP2pManager` + `Channel` + `GroupInfoListener` + `WifiManager` + `ConnectivityManager`），归 `EasyConnectService` 统一宿主。
5. **"手机给车机共享网络"是独立子系统**：`NetLinkService`（DNS 代理 + tun2socks 进程）+ `libDnsProxy.so` + `libtun2socks.so`，镜像连上后按配置项 `MIRROR_CONNECTED_OPEN_VPN` 自动 `startNetworkShare()`。
6. `ECOptions` 里有 **`useJavaBindTransport` / `useSubProcess` / `useDefaultMdnsPort`** 等开关 —— 亿连**保留了一套 Java 实现的传输绑定**，与 native 实现并存，按车型/平台切换（对我们有直接参考价值）。
7. 第三方依赖重：**ExoPlayer2 745 类**、华为 HMS 539、腾讯 Tinker+Bugly 330、友盟 240、阿里 fastjson 193；应用本体代码约 **1069 类**（`net.easyconn.*` 60 + 混淆包 `d/e/f/g` 1009）。

## 1. 分析工具链与方法

REA 自己**不做反编译**，它是"Agent ↔ 逆向工具"的桥。本次 Android 链路：

| 环节 | 实际用的东西 |
|---|---|
| REA CLI | `rea` 6.4.0（`npm i -g rea-agents`，本机 npm 全局装） |
| 反编译引擎 | `jadx-headless-mcp-0.7.1-all.jar`（REA 官方审计的固定 sha256，我下载后逐字节核对一致） |
| JVM | Temurin JDK 21.0.12.1（REA 要求 **完整 JDK 17+ 含 jdk.compiler**；本机原装只有 JDK 11，另下的） |
| 环境变量 | `REA_JADX_MCP_JAR`、`JAVA_HOME` 指向上述两者 |

用到的 4 个 REA 命令（复现时直接照抄，`$APK` = APK 绝对路径）：

```sh
export REA_JADX_MCP_JAR=/tmp/opencode/tools/jadx-headless-mcp-0.7.1-all.jar
export JAVA_HOME=/tmp/opencode/tools/jdk-21.0.12.1+1

rea inspect-android-package "$APK"                 # manifest / 权限 / 版本 / 类数
rea search-android-classes  "$APK" ""              # 全量类清单（3299）
rea inspect-android-class   "$APK" <全限定类名>     # 成员清单（方法+字段+内部类）
rea inspect-android-method  "$APK" <类> <方法>      # 反编译方法体（Java）
rea trace-android-references "$APK" <类> --method-name <方法>   # 谁调用了它
```

> **注意**：`inspect-android-class` 的内部类名用 **`.` 分隔**（`net.easyconn.ecsdk.ECTypes.ECTransportType`），
> 写成 Java 惯例的 `$`（`ECTypes$ECTransportType`）会报 `Exact class not found`。
> `trace-android-references` 的 `--method-name` **不能用于重载方法**（如 `bindTransportDevice` 有 4 个重载，REA 明确拒绝而不猜）——这是它的设计原则：歧义一律报错，不静默选第一个。

## 10. 对照 CarLife（结合既有两份报告）

| 维度 | 亿连 7.0.1 | CarLife 1.6 车机端（本项目） |

**可直接借鉴的三条**（不改代码，仅结论）：
1. **`useJavaBindTransport` 的存在**说明亿连遇到过 native 传输在某些机型不可用的情况，留了 Java 后路 —— 与我们 1.42 起"能用 Java 就别赌 native/隐藏 API"的教训同源。
2. **`socketTimeoutPeriod` 可配** —— 我们心跳超时 30s/120s 是写死的，亿连做成配置项。
3. **镜像成功后自动 `startNetworkShare()`** —— "连上就顺手把网络共享给车机"是留存体验的关键一环。

## 11. REA 的能力边界与本次局限（诚实说明）

REA 自己在每条 Evidence 里都带 `limitations`，原样摘录四条：

1. **静态反编译结论不能证明运行时行为**（APK 全程未执行）。
2. 方法签名是**引擎显示类型**，DEX 描述符与指令偏移未知；overload 索引只在本 artifact 内有效。
3. 类清单基于解析元数据，**可能含反编译源码里看不到的合成成员**，源码位置未知。
4. Manifest 摘要字段由上游引擎提取，**签名验证 = `not_performed`**；split APK、native 库分析、运行时捕获都不在该 provider 能力内。

本次**没做到**的：

- **native 协议栈未反编译**（`libECSDK.so` 的端口表、握手包、加密方式）——需要接 Ghidra/Hopper/IDA provider。Ghidra 支持本机 Linux/aarch64 未验证，是下一步。
- §5 里的 native 字符串佐证（AAC/RTSP 等）是本机 `strings` 直接扒的，**不是 REA 产出**，我在文中标注了"补充取证"。
- 未做动态分析（无设备/模拟器接入 REA 的 adb provider）。
