# 亿连手机互联 V7.0.1（车机端）「WiFi传输速率低 → 断连」分析报告

- 分析对象：`亿连手机互联V7.0.1.apk`（包名 `net.easyconn`，**这是车机端**；配套手机端是 `net.easyconn.carman` 亿连驾驶助手，见 `assets/EcConfig.prop` 的 `PHONE_APP_PKG`）
- 分析方式：jadx 反编译 3293 个 Java 类 + apktool 反编译资源 + 对 `libECSDK.so` / `libmediaserver.so` 做符号与字符串静态扫描
- 日期：2026-09-21

---

## 0. 结论速览（先看这个）

| 问题 | 结论 |
|---|---|
| 「WiFi传输速率低」是什么 | **不是测带宽**，是**每 2 秒 ping 一次对端的往返时延（RTT）监控**。单次 >200 ms 记 1 次，**连续 3 次**就弹提示（最快 6 秒弹出） |
| 这个提示会导致断连吗 | **不会**。它只做两件事：`Toast` 弹字 + 隐藏一个占位 View。断连另有原因 |
| 那为什么"先提示后断" | **同因两果**：链路质量下降同时触发（a）ping 时延超标 → 提示，（b）控制/数据 socket 超时或 AirPlay 镜像流中断 → 断连 |
| 断连真正的判定处 | 原生层 `[CtrlSocket]onDisconnect` / `[DataSocket]onDisconnect` → Java 层 `onMirrorDisconnected()` → `r0.x(4)` 拆界面 |
| 车机端有自动重连吗 | 有，但**很弱**：`p3.onMirrorRequestReconnect()` 是**空方法**；只有 `onPhoneAppExited` 会延迟 2 秒重开 transport（且 USB 专用开关 `APP_USB_EXITED_RECONNECT` 控制） |
| 什么时候才会弹这个提示 | **只在 WiFi 通道**。`q.l0()`（startMirror）成功后判断 `ECTransportType.name().contains("WIFI")` 才启动监控 → 走 USB / Miracast / DLNA 时**永远不会**弹 |

**一句话**：你看到的提示是个"迟到的报警器"，它响的时候链路已经不行了；断连是链路劣化的最终结果，不是提示造成的。

### 1.4 ping 是原生实现

```
net.easyconn.ecsdk.ECSDK.ping(String, int)  →  native_ping()
JNI 符号: Java_net_easyconn_ecsdk_ECSDK_native_1ping
所在库:   lib/arm64-v8a/libECSDK.so
```

同时 native 里还有一个可协商字段 **`socketTimeoutPeriodWifi`**（在 `[C2PService]sendClientInfo` 里随客户端信息一起发给手机），说明 socket 超时是**车机与手机协商**出来的，不是单端写死的。

### 1.5 监控的生命周期（已从 smali 逐指令确认）

监控开关是 `r0.s`（**volatile boolean**）。全包只有三处碰它：

| 位置 | 动作 |
|---|---|
| `r0.<init>` | `s = false`（初始关） |
| **`f.a.i.i.q.l0()`（= `startMirror()`）** | **`s = true`** ← 唯一打开的地方 |
| `r0.p0()`（由 `p3.surfaceDestroyed` 调用） | `s = false` ← 关闭 |

`q.l0()` 的真实片段（`q.smali:5742-5915`）：


（`r0.m` 是 lambda 桥：`new Thread(runnable, "Mirror_Presenter_Ping_Service")`；
`r0.m` 是 `Runnable`：`run() { r0.this.o(); }`）

> **★★ 关键限定：监控只在"传输类型名包含 WIFI"时启动。**
> `ECTransportType` 枚举里满足条件的是：
> `EC_TRANSPORT_ANDROID_WIFI(2)`（安卓无线，**直连与热点都走这个**）、
> `EC_TRANSPORT_IOS_WIFI_APP(6)`、`EC_TRANSPORT_IOS_WIFI_AIRPLAY(7)`。
> 不满足的：全部 USB（0/1/3/4/5/8）、`MIRACAST(9)`、`DLNA(10)`、`BLE(11/13)`、`BTRFCOMM(12)`。
>
> 也就是说：**只有无线（WLAN 直连 / 热点）才会弹「WiFi传输速率低」；走 USB 时永远不会弹**。
> 这也解释了为什么这个提示总跟"无线连接不稳"绑在一起。

线程池参数：`corePoolSize=1, max=1, keepAlive=1s, LinkedBlockingQueue` → 单工作线程。
循环靠 `while(s)` 存活；`p0()` 置 `s=false` 后下一轮退出，1 秒后线程被回收。

## 2. 证据链②：断连到底发生在哪一层

### 2.1 传输结构（原生字符串已还原出通道划分）

亿连车机端不止一条连接，原生 `libECSDK.so` 里能直接看到 5 类 socket 的断开日志模板：

```
[CtrlSocket]onDisconnect: ctrl socket disconnected, code=%d      ← 控制通道
[DataSocket]onDisconnect: data socket disconnected, code=%d      ← 数据通道
[C2PSocket]onDisconnect: c2p socket disconnected, code=%d        ← 车→手机
[P2CSocket]onDisconnect: p2c socket disconnected, code=%d        ← 手机→车
RTSPSocket / RTPSocket Disconnected begin/end                    ← AirPlay 音视频流
```

### 2.2 断开链路（已确认的调用路径）

```
native: [CtrlSocket]onDisconnect: onMirrorDisconnected begin/end
   ↓
native: [%s]onMirrorDisconnected: post event ET_STATUS_MIRROR_DISCONNECTED
   ↓
Java:  f.a.i.i.m.onMirrorDisconnected()          // m.java:459
         → g0.i0(4)                              // 主界面
         → r0.x(4)                               // 镜像 Presenter 拆除
              x(int) 里打印 " MirrorPresenter onMirrorDisconnected reason = 4"
```

界面随后显示 `yltp_status_tip4_txt1 = 屏幕镜像已断开`（配 `yltp_status_tip4_txt2 = 恢复屏幕镜像` 按钮）。

**已知的 reason 码**（`g0.i0(int)` 的实参）：

| reason | 来源 | 含义 |
|---|---|---|
| `4` | `m.onMirrorDisconnected()` | 镜像断开（正常的断开路径） |
| `5` | `q.l0()` 里 `startMirror()` 返回非 0 | 镜像**启动失败** |

`startMirror()` 的返回值也有区分：`-1 / -2 / -3 / -7` 有专门分支（`-7` 一条单独路径，`-3/-2/-1` 归到另一条），其它非 0 值统一走"failed"分支 → `i0(5)`。**这几个负数就是"为什么没起来"的直接线索，抓到日志一定要记下来。**

### 2.3 视频流侧的"正在劣化"信号

```
AirplayModel::recvMirrorThread(), running data inavailable mMirrorPause = %d, mMirrorDroped = %d
AirplayModel::recvMirrorThread(),header failed.
AirplayModel::recvMirrorThread(),value is lost,value=%d.
```

`mMirrorDroped` 持续上涨 + `header failed` = 视频包已经在丢/乱序了 —— 这通常**早于** socket 断开。

### 2.4 心跳通道

```
[C2PService]startHeartbeat: heartbeat thread is already running
heartbeat request already pending
peer does not accept heartbeats
```

出现后两条说明心跳通道被堵住或对端拒绝，是断连前的高危信号。

### 2.5 重连（弱）

```java
f.a.i.i.m.onPhoneAppExited() {              // m.java:884
    ...
    if (transport 是 USB) {
        if (!APP_USB_EXITED_RECONNECT) return;   // 默认 true，仅 USB 生效
    }
    // 等 2000 ms 再 openTransport
}

p3.onMirrorRequestReconnect() { }           // p3.java:939-940  ← 车机端是空实现！
```

协议里协商了 `supportMirrorReconnect` 标志，但**车机端收到重连请求后什么都不做**，只能等手机侧发起。

## 3. 为什么车机端会先报低速（按可能性排序）

| # | 原因 | 为什么 | 怎么验证 |
|---|---|---|---|
| 1 | **2.4G 信道拥堵 / 同频干扰** | GO 通常落在 2.4G 的 1/6/11 之一，和蓝牙、邻居 AP、微波炉重叠；空口一忙 RTT 立刻上 200 ms | 日志里看 `WifiP2pService` 的 operating channel；用手机 WiFi 分析仪看同频 AP 数 |
| 2 | **手机侧省电** | 息屏后手机 Wi-Fi 进 PS（省电）模式，收发要等 beacon，RTT 直接翻倍 | **保持手机亮屏再跑一次**，如果 5 分钟不掉 → 就是这个 |
| 3 | **车机 WiFi 芯片本身弱 + GO 并发** | GO 既要当 AP 又要收 AirPlay 视频 + 音频 + 触摸，空口上下行都拥挤 | 对比"车机热点模式"和"手机热点模式"是否也掉 |
| 4 | **距离/遮挡导致速率回落** | 5G 掉到 2.4G 或 MCS 降档 | 贴近测试 |
| 5 | **码率超过空口能力** | 编码输出 > 空口实际吞吐 → 缓冲堆积 → RTT 涨 → 最终丢包断链 | 降分辨率（见第 6 节）后观察是否改善 |

> 提示里的"速率低"三个字有误导性：它测的是**时延**。但对投屏来说，时延飙高往往确实意味着空口已经在排队 —— 所以这个报警虽然不是"测速"，指向却不算错。

### 4.5 判定表：从日志分辨到底是哪一种断法

| 日志特征 | 结论 | 对应处置 |
|---|---|---|
| `Ping ip:...pingTime:3xx` 连续 ≥3 条，**随后**才 `ctrl socket disconnected` | 链路**真的**劣化（时延→丢包→断） | 换信道 / 改 5G / 降分辨率码率 |
| 完全没有 ping 超时，直接 `ctrl socket disconnected, code=104 (ECONNRESET)` | 对端**主动**断开（手机切后台/被杀/息屏） | 手机省电白名单、锁后台 |
| `mMirrorDroped` 持续增长 + `header failed` | 视频包丢/乱序，解析失败 | 降码率、提信号 |
| `heartbeat request already pending` / `peer does not accept heartbeats` | 心跳通道堵死 | 同上 |
| `[P2CSocket]`/`[C2PSocket]` 断开**早于** `[CtrlSocket]` | 某一方向通道先挂 | 看是哪侧发起 |
| `onDisconnect code` 全都是同一个值、且每次都一样 | 可定位到固定的系统 errno | 按 errno 查（104=ECONNRESET, 110=ETIMEDOUT, 32=EPIPE） |

### 4.6 有个更直观的招：开 FPS 浮层

```
配置键 SHOW_FPS=true   或   prefs 写 key_ec_show_fps_state=true
```

`p3` 会在镜像界面底部中间加一个 20sp 的 TextView 并由 Handler 周期刷新（`MirrorFragment addFpsTextView`）。
**把掉帧/卡顿和「速率低」提示出现的时间点对齐看**，能立刻分辨"是网络在烂"还是"是解码/渲染在烂"。

## 5. 先不改任何东西，可以做的四组实验（建议按顺序）

1. **保亮屏对照**：同一位置、同一距离，手机**保持亮屏**跑 10 分钟 vs 让它息屏跑 10 分钟。
   - 只有息屏掉 → 手机 Wi-Fi 省电模式问题（最常见）
2. **换网络形态对照**：`WLAN 直连` vs `车机开热点` vs `手机开热点`。
   - 只有直连掉 → 是 P2P GO 的信道/空口问题（GO 常常被迫用某个固定信道）
3. **看信道**：`adb shell dumpsys wifi | grep -i p2p`，看 operating channel 是不是 1/6/11 且被占满。
4. **拉距离**：1 米内 vs 正常位置，如果 1 米内就正常 → 纯信号问题。

这四组做完，基本上能把范围锁到"手机省电"或"信道/空口"这两类。

## 6. 真要改的话，改哪里（先不动手，只列方案）

### 6.1 ⭐ 首选：`/etc/ec.conf`（**不用重打包 APK**）

亿连有个**外部配置文件热读**机制，已确认在正常启动流程里会被加载（`EcApplication.java:268 → f.a.i.m.d.e(this)`，本包 `FLAVOR=3`，不满足跳过条件 1/2，所以**一定会读**）：

```java
// f.a.i.m.d.e(Context)
if (G(context) == 1 || G(context) == 2) return true;   // FLAVOR=3，不走这里
new FileInputStream(new File("/etc/ec.conf")) ...       // ← 读它
f.a.i.m.d.f2935c = properties;                          // 全局可用
```

**同一个文件里还能覆盖这些键**（已从代码里逐个确认）：

| 键 | 作用 | 对"低速断连"的价值 |
|---|---|---|
| **`mirror_width`** | 覆盖投屏宽度 | ⭐⭐⭐ 直接降码率，最有效 |
| **`mirror_height`** | 覆盖投屏高度 | ⭐⭐⭐ 同上 |
| `video_codec_name` | 强制指定解码器名（默认 `video/avc` 自动选） | ⭐⭐ 换软/硬解，降车机压力 |
| `codec_color_format` | 指定解码输出色格式 | ⭐ 兼容性 |
| `keep_screen_bright` | 保持常亮 | ⭐ |
| `support_bt_call` | 蓝牙通话 | — |
| `float_size` / `float_show_app_to_front` | 悬浮按钮 | — |
| `fullScreen` | 全屏 | — |
| `flagIosInputBuffer` | iOS 输入缓冲 | — |
| `enable_ios_decode_px3` | iOS 解码 | — |
| `license_path` | 授权目录 | — |
| `project_flavor` + `conn_type` | **改传输通道组合**（位掩码：USB / WLAN直连 / iOS / QT / AirPlay 等） | ⭐⭐ 可用来强制只走某种通道 |

用法（车机需 root 或 `/etc` 可写）：

```bash
# /etc/ec.conf 就是标准 Java .properties 格式
cat > /etc/ec.conf <<'EOF'
# 把投屏分辨率降下来，从源头减空口压力
mirror_width=1024
mirror_height=600
EOF
chmod 644 /etc/ec.conf
# 重启亿连车机端 App 生效
```

> ⚠️ 注意：`/etc` 在 Android 上是 `/system/etc` 的软链，通常要 root + remount 才能写。如果车机没 root，这条路走不通 → 见 6.2。

### 6.2 次选：改 `assets/EcConfig.prop` 后重打包（**需要重打包 APK**）

`assets/EcConfig.prop` 只从 `context.getAssets()` 读，**无法外部覆盖**。可调且相关的键：

| 键 | 当前值 | 含义 | 建议试 |
|---|---|---|---|
| **`MEDIA_LEVEL`** | `1` | 0=LOW / 1=MIDDLE / 2=HIGH 画质档（→ `ECMediaLevel`，直接影响码率） | **先改 0** |
| `SOCKET_TIMEOUT_PERIOD` | *未设置* | 传给 native 的 socket 超时；另有 `socketTimeoutPeriodWifi` 变体 | 试探性调大，避免"稍慢就断" |
| `SHOW_FPS` | `false` | FPS 浮层 | 调试期改 `true` |
| `TYPE_MIRROR_MODE` | `0` | 镜像模式（代码里 0/1/2 三种） | 试 1 / 2，看是否换到更稳的通路 |
| `OPEN_TRANSPORT_RETRY_TIME` | *默认* `1000` | transport 重连重试间隔 ms | 保持 |
| `APP_USB_EXITED_RECONNECT` | `true` | 手机 App 退出后自动重开（**仅 USB**） | 无线场景无效 |
| `ENABLE_APP_WIFI_DIRECT` | `true` | WLAN 直连通道（App 侧） | 别关，直连就靠它 |
| `ENABLE_SDK_WIFI_DIRECT` | `false` | WLAN 直连通道（SDK 侧） | 可对比试着开 |
| `SUPPORT_SCREEN_MIRRORING` | `true` | 镜像总开关 | 别动 |
