# 热点开机自启 —— 冷启动 / 快照验证方案 v2（QuickBoot 环境）

设备：Telechips TCC893X / Android 4.4.2 eng / BCM4339 / 已 root
USB 序列号：000018030809054701DC ｜ 无线：10.24.26.190:5555

> v2 修订：修掉 v1 的 2 个 P0（阈值占位符、属性穿不透快照）+ 1 个 P1（init 同步 exec 阻塞）+ 修正开关 C 语义反了。新增"快照重拍是否曾经成功"的前置判定：00:02 执行 `quickboot create snapshot image` 后设备在 00:08 关机，但 `/data/hibernate/*` 的 mtime 仍是 2017 —— 高度怀疑它没成功，是被 watchdog 强杀的。

---

## 一、事实基线（已验证，勿重复验证）

| 事实 | 证据 |
|---|---|
| 手动热点链路可用 | `op_mode=2` + hostapd + dnsmasq + `wlan0=192.168.43.1`，Redmi-K70 已连上并拿到租约 |
| 重启走 QuickBoot 快照恢复 | `booting count` 每次 +1（376→377→378）、dmesg `Kernel restored from QuickBoot image` |
| 快照是旧镜像 | `/data/hibernate/*` mtime = `2017-01-01 08:02` |
| 运行进程不跨重启 | 重启后 hostapd(3838)/dnsmasq(3975) 全消失，`op_mode` 变空 |
| 钩子文件在盘上 | `grep -a 'boot_hotspot.sh' /dev/block/mmcblk0p2` 有字节；`drop_caches` 后 `ls` 立即可见（1105B, root:root, 755） |
| init 因陈旧 dcache 判它不存在 | dmesg `init: cannot find '/system/etc/install-recovery.sh', disabling 'flash_recovery'` |
| quickboot 是 PIE，阈值抠不出 | 字符串经 GOT 间接引用，GOT 槽在文件内为 0，静态分析拿不到 aging 阈值常量 |

**已排除路线（别再试）**：改 `/init.rc`（`/` 是 rootfs，`mount rootfs rootfs / ro remount`，重启即还原）、`start-ssh`（disabled 无 start）、`pppd_gprs`（disabled）、App 收广播（无 `CAP_SYS_MODULE`）。

## 三、阶段 1：起热点当兜底（建议走无线，避免 SIGTERM 干扰）

**优先用无线 adb 执行本阶段**：`adb -s 10.24.26.190:5555 shell ...`。脚本内 `settings put global wifi_on 0` 会让 USB 复合设备重枚举，本地 USB 会话必被 SIGTERM；用无线通道可连续观察。

```bash
adb shell "echo ap > /data/local/hotspot/mode"
adb shell "rm -f /data/local/hotspot/running.lock /data/local/hotspot/failcnt /data/local/hotspot/DISABLED"
adb shell "sh /data/local/hotspot/boot_hotspot.sh"     # 60~90s，会话可能断，属正常
```

**验证（90s 后）**：
```bash
adb shell "cat /sys/module/bcmdhd/parameters/op_mode"          # 2
adb shell "ps | grep -E 'hostapd|dnsmasq' | grep -v grep"      # 各 1
adb shell "ifconfig wlan0"                                      # 192.168.43.1 running
adb shell "grep -E '^ssid|^wpa_passphrase|^wpa_psk' /data/misc/wifi/hostapd.conf"
```

**通过**：`op_mode=2` + 两进程 + wlan0 有 IP；手机能搜到 `9B66BEB4` / `12345678` 连上。
**SSID 一致性**：手机验收前先看 `hostapd.conf`；netd 生成的是 `ssid=9B66BEB4`，passphrase 若显示 `wpa_psk=` 十六进制属正常（已 hash）。

## 四、阶段 2：只读取证（不改任何东西）

### 2.1 快照重拍是否曾经成功（决定走 A 还是走冷启动）

```bash
adb shell "ls -la /data/hibernate/"                     # mtime 是 2017 还是刚才？
adb shell "dmesg | grep -i -E 'hibernate|snapshot'"
adb shell "dmesg | grep -o 'booting count :[0-9]*'"
```

**判读**：
- mtime 仍是 2017 → 00:02 那次快照创建**没成功**（00:08 关机更像 watchdog 强杀），A 路线要先修创建动作
- mtime 变成刚才 → 快照创建成功，上电应已带回热点，直接跳阶段 4

### 2.2 属性层 + 文件层双读（P0-2 修正）

`setprop` 只保证写 RAM + `/data/property/`，而快照恢复可能用旧 dump 覆盖 RAM —— 必须两层都读并存基线：

```bash
for p in persist.sys.QB.aging.count persist.sys.QB.updated persist.sys.QB.user.allow persist.sys.QB.home.timeout; do
  echo "--- $p"
  echo -n "  RAM : "; adb shell getprop $p
  echo -n "  FILE: "; adb shell "cat /data/property/$p 2>/dev/null || echo '(no file)'"
done
echo "--- 快照时刻的属性 dump（恢复时可能按它回填）"
adb shell "grep -i QB /data/hibernate/properties"
```

**要点**：`/data/hibernate/properties` 是建快照时 `getprop > /data/hibernate/properties` 留下的。二进制里有 `Reloading properties - Timeout[%d]`，说明恢复后会**重新加载属性**——如果加载的是这份 dump，RAM 里改的属性会被盖回去。阶段 3 每次执行前后必须对读。

### 2.3 钩子的阻塞性（P1 修正）

```bash
adb shell "cat /system/etc/install-recovery.sh"
adb shell "command -v setsid; command -v nohup"
```

当前钩子是 `exec /system/bin/sh /data/local/hotspot/boot_hotspot.sh`（同步、约 70~90 秒）。**影响评估**：Android init 的 `oneshot` 由 init fork 后立即返回事件循环，`class_start main` 不会等它，所以**不阻塞开机**，代价只是这条服务占用 70~90 秒。若实测 `sys.boot_completed` 明显变晚，再改异步：
```sh
setsid /system/bin/sh $T >/dev/null 2>&1 &
```
**没有 setsid 时不要用裸 `&`** —— init 在服务主进程退出后会回收整个进程组，后台子进程会被一起杀掉（已实测复现）。

## 五、阶段 3：两条确定性路线（按顺序，不猜）

### 路线 A：热点运行态重拍快照（首选，最贴近真实用车）

原理：新快照若包含 hostapd/dnsmasq 与 op_mode=2 的驱动状态，上电 resume 即带回热点。

**先修好创建动作，用 mtime 作成功判据**（上次 rc=0 但没成功，返回码不算数）：
```bash
adb shell "ls -la /data/hibernate/"                                    # 基线
adb shell "/system/bin/quickboot create snapshot image"
adb shell "ls -la /data/hibernate/; dmesg | grep -i -E 'hibernate operation succeeded|Start creating snapshot'"
```
**成功判据**：`/data/hibernate/*` mtime 变为当前时间 **或** dmesg 出现 `hibernate operation succeeded`。
**失败判据**：mtime 不变且无成功日志 → 换 argv 变体（`quickboot create`）再试，**最多 2 种**，不无限试。

成功后设备自动断电 → 人工上电 → 阶段 4。若上电后 hostapd 在跑，**方案到此结束，不用碰冷启动**。

### 路线 B：确定性冷启动（A 走不通时）

**不做盲填阈值**（阈值是 PIE 内常量，静态抠不出）。改用行为判据：改属性，看下次启动是否变成完整 boot。每一步可回退。

```bash
# B1 基线
adb shell 'dmesg | grep -o "booting count :[0-9]*"'

# B2 双写：RAM + 文件层（P0-2）
adb shell "setprop persist.sys.QB.aging.count 99999"
adb shell "echo -n 99999 > /data/property/persist.sys.QB.aging.count"
adb shell "sync"

# B3 对读确认两层一致
adb shell getprop persist.sys.QB.aging.count
adb shell cat /data/property/persist.sys.QB.aging.count

# B4 重启观察
adb shell reboot
```

**冷启动成功标志（三者任一）**：
- `booting count` 归零
- dmesg 无 `restored from QuickBoot image`
- 开机耗时明显变长 / 出现完整 early-init 日志序列

**B 失败则试 B′**：`setprop persist.sys.QB.updated yes`（同样双写文件层）→ reboot → 同判据。
**最多两轮**，两轮都无标志就停手，转路线 C 或手动方案。

### 路线 C：让快照失效（直路，但必须先备份）

`/data/hibernate` 是快照的**元数据 dump 目录**，不是镜像本身（镜像在 `mmcblk0p9`）。删它能否让 bootloader 放弃快照取决于 quickboot 校验逻辑——**先 mv 备份再试，不直接 rm**：

```bash
adb shell "mv /data/hibernate /data/hibernate.bak_$(date +%H%M)"
adb shell reboot
```
- 冷启动成功 → 保留备份，确认钩子执行后再决定是否删备份
- 无变化 → `mv /data/hibernate.bak_xxxx /data/hibernate` 原样还原，零残留

**绝不做**：`rm -rf /data/hibernate` 不备份、碰 `mmcblk0p9`、碰 `by-name`、改 bootloader 参数。

## 六、阶段 4：核心验证（唯一硬判据）

```bash
# 1) 是否真冷启动（路线 B/C 才需要）
adb shell "dmesg | grep -o 'booting count :[0-9]*'"
adb shell "dmesg | grep -c 'QuickBoot image'"

# 2) 钩子有没有被执行 —— 最重要
adb shell "cat /data/local/hotspot/boot.log"
adb shell "cat /data/local/hotspot/boot.log.1 2>/dev/null"

# 3) init 还报不报找不到
adb shell "dmesg | grep -i 'flash_recovery'"

# 4) 热点是否自动起
adb shell "cat /sys/module/bcmdhd/parameters/op_mode"
adb shell "ps | grep -E 'hostapd|dnsmasq' | grep -v grep"
adb shell "ifconfig wlan0"

# 5) DHCP 是否分发
adb shell "cat /data/misc/dhcp/dnsmasq.leases"
```

**通过**：`boot.log` 出现**本次时间戳**的 `boot_hotspot start` **且** `op_mode=2` **且** 手机免手动可连。
注意区分：手机搜不到 ≠ 钩子没跑 —— 先看 `boot.log` 再下结论。

## 七、结果分支

| 阶段 4 现象 | 判定 | 下一步 |
|---|---|---|
| `boot.log` 有本次记录 + 热点起 | 成功 | 清理探针文件，交付 |
| `boot.log` 无记录，init 也不再报找不到 | init 找到但没执行 | 查钩子权限/shebang；改 init 直调 `/system/bin/sh <脚本>` |
| `boot.log` 无记录，init 仍报找不到 | 没真冷启动 | 换 B′ 或 C，最多两轮 |
| 钩子跑了但热点失败 | 脚本问题 | 看 `boot.log` 的 `FAIL stepN`（脚本已 `restore_sta()` 兜底，WiFi 不会丢） |
| 热点起但手机连不上 | 驱动 resume / 信标 | 抓 `dmesg \| grep -i 'AP/GO\|SoftAP\|beacon'` + hostapd logcat |

## 十、风险边界（红线）

1. 不动 `/init.rc`、不动 `mmcblk0p9`、不动 `by-name` 分区、不动 bootloader 参数。
2. `/data/hibernate` 只 `mv` 备份，不 `rm -rf`。
3. `boot_hotspot.sh` 里的 `wifi_on 0` 会让 USB 重枚举 → 会话 SIGTERM 是正常现象，不是车机故障。
4. adb 失联恢复顺序：无线 `10.24.26.190:5555` → 插拔 USB 线 → 车机断电重启。
5. 冷启动实验最多 2 轮，两轮无标志就停手转手动方案，不在"猜语义"上消耗车机寿命。
